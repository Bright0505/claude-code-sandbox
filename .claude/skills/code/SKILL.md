# 寫程式碼

`CLAUDE.md` 已定義鐵則 1-3。`verify` 講「怎麼證明改對了」，
本 skill 講**動手前怎麼確認改法是對的，以及過程中怎麼守住範圍**。

五個檢查點，按時間順序排。

---

## 1. 估範圍前：source of truth 優於 documentation

Migration guide 說「應該長什麼樣」，原始碼說「實際接受什麼」。
**會改變影響範圍的關鍵假設**（這個 API 吃什麼型別、有沒有預設值、
相容層還在不在）先讀實作再定案，不要憑文件字面估一個範圍再被迫重估。

> 實例：文件說 handler 要回傳框架自己的物件，照字面理解得重寫整個邏輯層；
> 讀序列化函式才發現它接受裸 dict —— 範圍從 6+ 檔收斂回 3 檔。

---

## 2. 套用時：逐 call site 驗證，同構不代表同值

同一種改法套 N 個檔案，只降低了「猜改法對不對」的成本，
**不降低逐一驗證的必要** —— 結構相同的地方可能各自帶著只有那裡才有的變體。

> 實例：三個入口套同一種 handler 改法，前兩個原本就回傳 dict 直接過；
> 第三個是獨立寫的重複邏輯、回傳裸 list，序列化層直接拒收。

---

## 3. 改完：dead code elimination

改動簽名或呼叫方式，會讓支撐舊寫法的 import／型別／分支變成死碼，
而它們**不會主動報錯**。改完回頭掃一次該檔頂部，交給 linter 確認 ——
規則通常本來就開著，但沒跑就會進 commit。

---

## 4. 驗證：mutation 用 VCS 取回舊版，不手寫變體

`verify` 要求新測試要故意弄壞一次確認轉紅。改既有程式碼時，最可靠的弄壞方式是：

```bash
git checkout <base> -- <檔案>   # 取回真正的舊版
# 跑新測試 → 應該全紅
git checkout HEAD -- <檔案>     # 還原 → 應該全綠
```

不要憑印象手寫一個「假設會失敗」的變體 —— 那是腦補出來的近似版，會失真。
**轉紅時要確認失敗原因跟預期一致**，不是隨便哪裡壞了也算數。

---

## 5. 全程：scope guard

改一個地方時順手發現的既有問題，判準只有一條：
**它會不會讓「這次改動」過不了驗收？**

| 情況 | 動作 |
|---|---|
| 會擋住驗收 | 這次修 |
| 不擋 | 只記錄，不動手 |

判斷「是不是這次造成的」用 `git show <base>:<檔案>` 查證，不要憑感覺。
不擋驗收卻順手修下去，是範圍在無聲膨脹。

---

## 收尾：clean code

- [ ] 死 import／型別／分支清掉了嗎（linter 實際跑過）
- [ ] 每個 call site 都獨立驗過，不是靠「結構一樣」推論
- [ ] 這次撞到但沒修的既有問題，記錄了嗎
