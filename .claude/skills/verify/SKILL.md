# 驗證

`CLAUDE.md` 已定義相關鐵則。本 skill 是「宣稱驗過了」這件事的具體做法。

---

## 核心原則：一手來源優於二手

別人（包含使用者）的陳述是**意圖層**的資訊，不是事實。要寫進結論前，先問
「這是我親眼看到的輸出，還是有人告訴我的」。

**判準不是「不信任使用者」，是「結論要自己能重現」**——陳述可以當線索去查，
不能直接當結論用。查證的成本通常遠低於查錯之後要收拾的成本。

實例：使用者說「我已經完成所有 PR」。沒有直接寫進紀錄，改用 GitHub 公開 API
（`api.github.com/repos/<owner>/<repo>/pulls?state=all`）查每個 PR 的 `merged`
欄位，確認全部 `true` 之後才記進任務檔——而且順手用這次查證帶出一個新資訊：
公開 repo 的 `git fetch`／`ls-remote` 走 HTTPS 完全不需要認證，解決了原本
「沒有 ssh client 所以做不到」的另一個問題。**查證常常比預期多帶回一點東西**，
單純採信不會有這個副產品。

---

## 寫測試：沒紅過不算測試（鐵則 4 的具體流程）

1. **先跑一次現有測試，記下 baseline**——沒有 baseline，改完測試全過也無法
   證明「原本能做的還能做」，只能證明「新東西看起來對」
2. **新測試要故意弄壞被測目標一次，確認測試真的轉紅**——不是「我覺得邏輯對
   就跳過這步」。跳過這步等於沒驗證測試本身有沒有斷言錯位置、有沒有寫成
   恆真式
3. 還原，確認轉綠
4. 過程中抓到的紅燈**不是意外的雜訊，是這個流程本來要做的事**

實例：D7 結構檢查腳本第一版寫完，用 14 則故意壞掉的 fixture（每種檢查各一個）
跑過一次，抓到 2 個真的邏輯錯——原子性判斷誤把「已歸檔的 stub 列」算進主檔
集合、其中一個測試 fixture 本身漏填必要欄位（狀態寫「已修」卻沒填「守備」，
觸發了另一個不相關的檢查）。修完才是真的驗過，不是寫完就當作驗過。

---

## 每次改動後的回歸檢查

- 有現成測試套件時，**改完一律整套重跑，不是只跑新加的部分**——只跑新測試
  只能證明新東西沒錯，證明不了「原本能做的還能做」
- 沒有現成測試套件、或改的是文件／規範本身時，退化成「有沒有可觀察的行為
  改變」——例如結構檢查腳本對現有真實資料重跑一次，確認輸出乾淨且沒有
  新冒出來的警告

---

## 別讓檢查工具自己過度宣稱（鐵則 9 的具體做法）

一個檢查只能宣稱它**真的檢查過**的東西，不能讓輸出被讀成它連帶保證了
沒檢查過的東西。

具體做法是**區分「錯誤」跟「需要人判斷的提示」**：

| 類型 | 語意 | 範例 |
|---|---|---|
| 錯誤 | 事實性、可判定，擋流程 | 指向的 ID 不存在、路徑不存在 |
| 需要人判斷的提示 | 只是攤出一個事實，不代表任何結論，不擋流程 | 「影響範圍」提到的檔案已經不存在——**不代表可以歸檔**，只代表「需要人去判斷這個故障形態是否還可能發生」 |

每次工具跑完，順手檢查輸出有沒有講清楚**「沒檢查什麼」**，不是只講
「檢查了什麼」——命名也要避免讓綠燈被過度解讀（例如不要叫「驗證關聯性」，
那是語意層，這個工具做不到）。

---

## 環境能力要驗證，不能假設

承諾一個動作（push、開 PR、跑某個指令）之前，**先驗證環境真的做得到**，
不是假設「應該可以」再去試，試失敗才回頭查原因。

具體做法：

```bash
gh auth status
which ssh
env | grep -iE "GH_TOKEN|GITHUB_TOKEN"
```

三者都沒有，就是真的做不到——直接說清楚環境缺什麼，附上實際跑的指令跟輸出
（不是「我猜這裡應該不能 push」）。**「做不到」跟「沒試」是兩個不同的結論**，
前者要有查證過程撐著，後者只是還沒查。

反過來也一樣：不要因為「這個動作以前不行」就假設現在也不行。
上面 HTTPS 讀取不需要認證那個例子就是先查再說，沒有被「沒 ssh 所以整條路都
斷了」這個直覺結論卡住。
