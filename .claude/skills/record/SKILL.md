# 記錄與回查

三個地方，職責不重疊：

| 檔案 | 記什麼 | 生命週期 |
|---|---|---|
| 計畫檔的「問題紀錄」 | **這個任務期間**遇到的問題 | 任務結束就定案 |
| `docs/KNOWN-ISSUES.md` | **未來任務需要知道**的坑 | 長期被 grep 回查 |
| `docs/DECISIONS.md` | 決定了什麼、**為什麼不是另一個** | 長期 |

---

## 1. 開工前：回查事故紀錄

用**要改的檔名**和**功能名**各查一次：

```bash
grep -n "<檔名>" docs/KNOWN-ISSUES.md
grep -n "<功能名>" docs/KNOWN-ISSUES.md
```

**有命中就要在計畫裡寫明怎麼避開**，不是看過就算。
這是 `plan` 第 2 步（定位）的一部分，但最容易被跳過 —— 跳過等於前人記的坑白記。

想知道「這塊以前為什麼做成這樣」，按時間讀 `docs/tasks/` 比讀程式碼快。

---

## 2. 問題發生時：triage

> **「下一個碰到這塊的人，不知道這件事會不會出事？」**
> 會 → `KNOWN-ISSUES.md`。不會 → 只留在計畫檔。

| 事件 | 記哪裡 |
|---|---|
| 測試 fixture 名字打錯、忘記加 import | 計畫檔 —— 下次不會因為不知道而出事 |
| 失敗時回「0 筆」而不是報錯 | **KNOWN-ISSUES** —— 下個人會誤判成真的沒資料 |
| 這個 image 沒有 curl，healthcheck 永遠失敗 | **KNOWN-ISSUES** —— 下次寫 healthcheck 會再踩 |

**不要每個 commit 都寫一則。** 那會讓 `grep <檔名>` 回一堆雜訊，
而檢索正是這個檔案存在的理由。per-commit 的「為什麼」已經在 commit 訊息裡，
再寫一份是重複，而重複的兩份一定會漂移。

---

## 3. 記錄時：KNOWN-ISSUES 條目格式

```markdown
### K-8 匯出功能在 SQL 失敗時回「共 0 筆」而不是報錯
- **影響範圍**：`export_handler.py`、所有會匯出的功能
- **狀態**：已修
- **守備**：`tests/integration/test_export.py::test_sql_failure_is_not_zero_rows`
  （mutation 驗證：還原 `export_handler.py:88` 的內層檢查 → 該測試轉紅）
- **症狀**：SQL 寫錯時使用者拿到一個空檔，以為真的沒資料
- **根因**：外層 `success` 恆為 true，錯誤藏在內層 `data.success`（`export_handler.py:88`）
- **判準**：0 筆時先用查詢工具覆驗一次
- **關聯**：與 K-3 同一個「錯誤被外層吃掉」形態
- **日期**：2026-08-05
```

| 欄位 | 作用 |
|---|---|
| **影響範圍**（最重要）| 讓回查變成一個指令。寫**檔名／模組名／功能名**，不要只寫抽象描述。<br>檔案改名時**累加不覆蓋**：`payment/checkout.ts`（原 `order/submit.ts`）—— 兩個名字都 grep 得到 |
| **症狀** | 實際觀察到什麼，**不是猜測** |
| **根因** | 查證後的原因，附證據（`檔案:行號`、實測輸出）|
| **判準** | **下次怎麼提早發現它。** 這一欄是條目的價值所在；沒有判準的條目讀了也不知道要做什麼 |
| **守備** | 哪個測試在守，**加上當初怎麼 mutation 驗證的**。狀態改 `已修` 時填，不要事後補（那時已沒人記得怎麼弄壞它）|
| **關聯** | 指向同形態的其他條目。**單向即可**（新指舊），工具把有向連結當無向處理。<br>⚠️ **這一欄會被忘記填**（尤其隔幾個月的同形態，當事人根本不知道有前例）——<br>所以**散佈度只會低估，不會高估**，低散佈度**不可**讀成「這裡健康」。<br>找同形態時除了跟著 `關聯` 走，也用 `症狀`／`根因` 的**措辭** grep（「回 0 筆」、「吞掉」、「靜默失敗」）|

### 狀態語意

| 狀態 | 意思 |
|---|---|
| `未處理` / `處理中` | |
| `已修` | 修好了**且** `守備` 已填 |
| `已修（無守備）` | 沒有測試守住 → **它會回來**，不可歸檔 |
| `已知未修` | 刻意不修（成本／取捨）。**永不歸檔** |
| `已推翻` | 原本的判定錯了。**保留原文**，標明推翻理由與日期 |

`已知未修` 與 `已推翻` **不可刪**（禁令 8）。刪掉的後果是下一個人重新調查同一件事、
得到同樣的結論。

ID 單一系列 `K-<n>`，遞增，**永不重用**。不分前綴 —— 需要區分時用內容講清楚。
**執行者自己的失誤也要記**（誤報完成、查錯位置、誤用指令）—— 對下一輪的價值不低於程式碼缺陷。

---

## 4. 任務結束時：escalation sweep

計畫檔裡的問題掃一次：符合 §2 標準的升級到 `KNOWN-ISSUES.md`，
計畫檔那則**保留**並在「已升級？」欄註明 ID。

---

## 5. 決策時：DECISIONS.md

**該問人的**：範圍取捨、架構投資、動到設定面／正式環境／外部可見行為、要花錢或花別人時間。
**該自己決的**：有慣例、有明顯正解、或錯了容易改回來。

```markdown
## D<n> — <問題>（待決 / 已決議：採 X）

**問題**：<為什麼需要決定>

| 選項 | 內容 | 代價 | 效果 |
|---|---|---|---|

**建議**：<明確推薦哪一個，以及為什麼>
**決議**：<採哪個。**為什麼不是另一個**。實作要點與實測結果。>
**日期**：
```

問人時用**選項表 + 代價 + 效果 + 推薦**，不要開放式問句。
「A 還是 B？」把工作推回去；「我建議 A，因為…，除非你要…」才是幫忙。

**決議一定要寫「為什麼不是另一個」** —— 只寫選了什麼，過幾個月排除的理由沒人記得，
於是又被重新提出。

---

## 6. 定期：archival

⚠️ 觸發時機與檔案組織方式**仍是待決事項**（見 `docs/DECISIONS.md` D1）。以下只列已定案的。

### 資格（全部成立才可歸檔）

1. 狀態為 `已修` / `已推翻` / `已被架構改動消滅`
2. `守備` 非空，且該測試**存在**、**現在是綠的**、有 mutation 驗證紀錄
3. 所屬關聯鏈上**沒有** `已知未修`
4. 沒有有效條目的判準依賴它的細節（**有的話先把細節複製過去**，這是可解的，不是死結）

**永不歸檔**：`已知未修`、`未處理`、`已修（無守備）`

### 三條硬規則

**① 主檔必須留 stub，且 stub 要含「影響範圍」的關鍵字**

否則 grep 失效 → 有人以為沒歷史 → 重踩一次。**這條沒做到，歸檔就是淨損失。**

```markdown
| ID | 一句話 | 影響範圍 | 明細 |
|---|---|---|---|
| K-8 | 匯出在 SQL 失敗時回 0 筆而非報錯 | `export_handler.py`、匯出功能 | [archive](known-issues-archive.md#k-8) |
```

⚠️ **影響範圍的檔案已被刪除時這條會失效**（沒人會 grep 不存在的檔案），
此時 stub 關鍵字改用**形態**。而且**檔案消失 ≠ 形態消失**：

| 情況 | 動作 |
|---|---|
| 檔案改名／搬移，功能還在 | 條目有效，更新 `影響範圍`（累加）|
| 檔案沒了，形態在新實作仍可能發生 | **不可歸檔** → 影響範圍指向新位置 |
| 檔案沒了，形態不可能再發生 | 可歸檔 |

不確定時**預設不歸檔** —— 誤歸檔的代價是坑被重踩且 grep 不到，誤保留只是多一則雜訊。

**② 歸檔是搬移不是刪除** —— 明細完整搬到 archive 檔，一個字都不刪，archive 進版控。

**③ 關聯群組是 atomic** —— 同一條鏈要嘛一起歸檔，要嘛都不動。
只搬走其中一則會讓「同一形態復發」看不出來。

### 流程

**一律先提清單等同意**（動到既有紀錄，且判斷密集）：
掃主檔 → 列出符合資格的與**不符合的（附理由）** → 確認後才動手 → 回報搬了幾則、留了幾則。

不符合清單有**兩種讀法**，同一次掃描零額外成本：

| 按什麼讀 | 得到什麼 |
|---|---|
| 缺 `守備` | **待補測試的清單** |
| 關聯鏈的**散佈度**（碰到幾個不同的 `影響範圍`）| **缺抽象的清單** |

第二種：按散佈度由高到低排序報前幾條，**不設門檻**（理由見 D6）。
注意散佈度看的是**幾個不同的地方** —— 同一形態在同一處復發三次是「修了沒守住」
（指向 `守備` 品質），不是架構問題。

**歸檔一直不動本身就是訊號** —— 鏈越長，鏈上出現 `已知未修` 的機率越高，整條鏈永遠凍結。
掃了半天沒東西能歸檔，看起來像很健康，其實是在說失敗形態不夠局部。

### 為什麼歸檔時不做 mutation 驗證

太貴，而且對舊條目**根本做不到**（沒人記得當初怎麼弄壞它）。
貴的驗證要在**修的當下**做，那時它很便宜（還原自己的修正就是 mutant）。
歸檔時只檢查「當初做過」的證據 + 跑那一個測試。

### 結構檢查腳本

已實作：`.claude/skills/record/scripts/check_known_issues_links.py`
（範圍與界線見 `docs/DECISIONS.md` D7）。

⚠️ **能力邊界**：`守備` 那項**只查測試路徑存在，不執行測試** ——
真的要驗「現在是綠的」需要跑 pytest，增加相依與執行時間，v1 刻意不做。
D7 的表述若讀起來像「保證為綠」，以本節為準（`verify` §4：工具不可 over-claim）。

它只驗**結構**那一層 ——
價值集中在此，因為這層的失效全是**靜默的**（原子性被破壞沒有外顯症狀、
檔案改名後條目看起來完全正常）。

三條紅線：

1. **不可命名為「驗證關聯性」** —— 綠燈會被讀成語意層的宣稱（見 `verify` §4）
2. **要有條目數斷言** —— 解析數必須等於 `^### K-` 的行數。
   這類腳本最常見的死法是解析不到東西 → 0 錯誤 → 綠燈，完全無聲
3. **腳本自己要有轉紅紀錄** —— 用故意壞掉的 fixture 確認每種錯誤都抓得到

**檔案不存在的輸出語意**：報「這則需要人判斷：形態還在嗎」，**不是**「可歸檔」。
腳本可以指出事實，不能推論結論。

有門檻、有啟發式的部分**仍要等真實樣本**，且只能標「候選，請人看」，不可報成錯誤 ——
否則有人會為了消警告亂連。
