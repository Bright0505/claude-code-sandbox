# 記錄與回查

三個地方，職責不重疊：

| 檔案 | 記什麼 | 生命週期 |
|---|---|---|
| 計畫檔的「問題紀錄」 | **這個任務期間**遇到的問題 | 任務結束就定案 |
| `docs/KNOWN-ISSUES.md` | **未來任務需要知道**的坑 | 長期被 grep 回查 |
| `docs/DECISIONS.md` | 決定了什麼、**為什麼不是另一個** | 長期 |

---

## 該記在哪裡：一句話標準

> **「下一個碰到這塊的人，不知道這件事會不會出事？」**
> 會 → `KNOWN-ISSUES.md`。不會 → 只留在計畫檔。

例子：

| 事件 | 記哪裡 | 為什麼 |
|---|---|---|
| 測試 fixture 名字打錯，改掉 | 計畫檔 | 只是這次的雜事 |
| 匯出功能在 SQL 失敗時回「0 筆」而非報錯 | **KNOWN-ISSUES** | 下個人看到 0 筆會誤判成真的沒資料 |
| 這個 image 沒有 curl，healthcheck 永遠失敗 | **KNOWN-ISSUES** | 下次寫 healthcheck 會再踩 |
| 忘記加 import，補上 | 計畫檔 | 下次不會因為不知道而出事 |

### 升級規則

任務期間記在計畫檔的問題，**任務結束時 sweep 一次**：符合上面標準的升級到
`KNOWN-ISSUES.md`，計畫檔那則保留並在「已升級？」欄註明 ID。

**不要每個 commit 都寫一則 KNOWN-ISSUES。** 那會讓 `grep <檔名>` 回一堆雜訊，
檢索價值消失 —— 而檢索正是這個檔案存在的理由。per-commit 的紀錄已經在 git log 裡了
（commit 訊息本來就要求寫「為什麼」），再寫一份是重複，而重複的兩份一定會漂移。

## KNOWN-ISSUES 條目格式

```markdown
### K-8 匯出功能在 SQL 失敗時回「共 0 筆」而不是報錯
- **影響範圍**：`export_handler.py`、所有會匯出的功能
- **狀態**：已修
- **守備**：`tests/integration/test_export.py::test_sql_failure_is_not_zero_rows`
  （突變驗證：還原 `export_handler.py:88` 的內層檢查 → 該測試轉紅）
- **症狀**：SQL 寫錯時使用者拿到一個空檔，以為真的沒資料
- **根因**：外層 `success` 恆為 true，錯誤藏在內層 `data.success`（`export_handler.py:88`）
- **判準**：0 筆時先用查詢工具覆驗一次
- **關聯**：與 K-3 同一個「錯誤被外層吃掉」形態
- **日期**：2026-08-05
```

### 各欄位的作用

**`影響範圍`（最重要）** —— 它讓回查變成一個指令。寫**檔名／模組名／功能名**，
不要只寫抽象描述。沒有這一欄，KNOWN-ISSUES 只能從頭讀，等於沒有檢索能力。

**`症狀`** —— 實際觀察到什麼，**不是猜測**。

**`根因`** —— 查證後的原因，附證據（`檔案:行號`、實測輸出）。

**`判準`** —— **下次怎麼提早發現它。** 這一欄是條目的價值所在；
只寫「發生了什麼」而沒有判準的條目，讀了也不知道要做什麼。

**`守備`** —— 哪個測試在守這件事，**加上當初怎麼突變驗證的**。
狀態改成 `已修` 時填，不要事後補（那時候已經沒人記得當初怎麼驗）。
它是「真的修好了」唯一可檢查的證據。

**`關聯`** —— 指向同形態的其他條目。同一個形態復發兩三次是很常見的，
關聯讓它看得出來。

### 狀態

| 狀態 | 意思 |
|---|---|
| `未處理` | 知道了，還沒動 |
| `處理中` | |
| `已修` | 修好了**且** `守備` 已填 |
| `已修（無守備）` | 修了但沒有測試守住 → **它會回來**，不可歸檔 |
| `已知未修` | 刻意不修（成本／取捨）。**永不歸檔** |
| `已推翻` | 原本的判定錯了。**保留原文**，標明推翻理由與日期 |

**`已知未修` 與 `已推翻` 不可刪**（禁令第 8 條）。
刪掉的後果是下一個人重新調查同一件事，得到同樣的結論。

### ID

單一系列 `K-<n>`，遞增，**永不重用**。不分「缺陷／執行者失誤」兩種前綴 ——
對讀者是多餘的認知負擔，需要區分時用內容講清楚就好。

**執行者自己的失誤也要記。** 誤報「已完成」、查錯位置得出錯誤結論、
改設定檔弄壞語法、誤用指令覆蓋掉剛做好的檔案 —— 這些對下一輪的價值
不低於程式碼缺陷。

## 開工前回查

這是 `plan` skill 第 2 步（定位）的一部分，但值得單獨說，因為**它最容易被跳過**：

```bash
grep -n "export_handler" docs/KNOWN-ISSUES.md
grep -n "匯出" docs/KNOWN-ISSUES.md
```

用**要改的檔名**和**功能名**各查一次。

**有命中就要在計畫裡寫明怎麼避開**，不是看過就算。跳過這一步，前人記錄的坑就白記了。

也別忘了 `docs/tasks/` —— 想知道「這塊以前為什麼做成這樣」，
按時間讀那裡的計畫檔比讀程式碼快。

## DECISIONS.md

記「這件事該由誰決定」，以及決定的理由。

**該問人的**：範圍取捨、架構投資、動到設定面／正式環境／外部可見行為、要花錢或花別人時間。
**該自己決的**：有慣例、有明顯正解、或錯了容易改回來。

```markdown
## D<n> — <問題>（待決 / 已決議：採 X）

**問題**：<為什麼需要決定>

| 選項 | 內容 | 代價 | 效果 |
|---|---|---|---|
| A | | | |
| B | | | |

**建議**：<明確推薦哪一個，以及為什麼>

**決議**：<採哪個。**為什麼不是另一個**。實作要點與實測結果。>
**日期**：
```

問人時用**選項表 + 成本 + 效果 + 推薦**，不要開放式問句。
「A 還是 B？」把工作推回去；「我建議 A，因為…，除非你要…」才是幫忙。

**決議一定要寫「為什麼不是另一個」。** 只寫選了什麼，過幾個月沒人記得排除的理由，
於是又被重新提出。

## 歸檔

⚠️ **歸檔的觸發時機與檔案組織方式目前是待決事項** ——
見本 repo `docs/DECISIONS.md` 的 D1。以下只列已定案的部分。

### 資格（全部成立才可歸檔）

1. 狀態為 `已修` / `已推翻` / `已被架構改動消滅`
2. `守備` 非空，且該測試**存在**、**現在是綠的**、有突變驗證紀錄
3. 所屬關聯鏈上**沒有** `已知未修`
4. 沒有有效條目的判準依賴它的細節（有的話先把細節複製過去）

**永不歸檔**：`已知未修`、`未處理`、`已修（無守備）`

### 三條硬規則

**1. 主檔必須留 stub，且 stub 要含「影響範圍」的關鍵字**

否則歸檔後 `grep` 失效 → 有人以為沒歷史 → 重踩一次。
**這一條沒做到，歸檔就是淨損失。**

```markdown
## 已歸檔

| ID | 一句話 | 影響範圍 | 明細 |
|---|---|---|---|
| K-8 | 匯出在 SQL 失敗時回 0 筆而非報錯 | `export_handler.py`、匯出功能 | [archive](known-issues-archive.md#k-8) |
```

**2. 歸檔是搬移，不是刪除**

明細完整搬到 archive 檔，一個字都不刪。archive 檔要進版控。ID 永不重用。

**3. 關聯群組是原子的**

同一條關聯鏈上的條目，要嘛（符合資格的）一起歸檔，要嘛都不動。
不可以只搬走其中一則 —— 那會讓「同一形態復發」看不出來。

### 流程

**一律先提清單等同意**（動到既有紀錄，且判斷密集）：

1. 掃主檔 → 列出**符合資格的**（ID／一句話／守備）與**不符合的（附理由）**
2. 對方確認 → 才動手
3. 回報：搬了幾則、留了幾則、各自理由

第 1 步的「不符合清單」很有用 —— 它會顯示有多少 `已修（無守備）`，
那本身就是待補測試的清單。

### 為什麼歸檔時不做突變驗證

太貴，而且對舊條目**根本做不到**（沒人記得當初該怎麼弄壞它）。

貴的驗證要在**修的當下**做，那時候它很便宜（還原自己的修正就是突變）。
歸檔時只檢查「當初做過」的證據 + 跑那一個測試 —— 四項機械動作，成本趨近於零。

這件事可以完全機械化成 CI 檢查（解析 `守備` 欄位 → 確認測試存在且綠），
成本是 CI 跑不是 Claude 跑。等有真實的 KNOWN-ISSUES 檔案再寫，
現在寫等於憑空猜解析格式。
