# 交付

`CLAUDE.md` 已定義相關禁令。本 skill 是它們在 commit／分支／push／PR／submodule
這幾個具體動作上的展開。**不重述**已在禁令裡講過的規則，只講「怎麼做」。

---

## Repo 過去的實際做法，不是核准的先例

即使 `git log` 顯示過去的 commit 是直接上在 `main` 上（違反禁令 1），
**不代表現在可以比照辦理**。歷史記錄的是「當時發生過什麼」，不是
「規範核准的例外」——兩者容易混在一起，因為都叫「這個 repo 一直是這樣做」。

實例：`mcp-fda` 的 `docs/tasks/HANDOFF.md` 有連續三個 commit
（`a57844d`／`9fc076a`／`10b1f54`）是直接 commit 在 `main` 上，事後才注意到
這違反禁令 1。發現落差時，正確處理**不是**兩個直覺反應的任何一個：

- 沿用歷史模式，比照直接 commit main（把既有違規當先例）
- 自己默默改成開分支（單方面改變既有工作方式，同樣是需要先講的決定）

而是把落差攤開講清楚——列出選項（沿用既有模式／改開分支走 PR／先不
commit）讓使用者選。使用者選了「開分支＋PR，照規範走」，等於確認
「歷史上的違規是疏漏，不是默許的例外」。

判準：**寫在 `CLAUDE.md` 的禁令，優先權高於「這個 repo 過去實際上怎麼做」**。
發現兩者不一致時，不要自己選一邊照做，先問。

## 分支與 commit：性質不同就分開

禁令 6「一個 commit 不混不同性質的改動」，展開到分支層一樣適用：
**兩個改動如果能各自獨立被接受或拒絕，就分開 commit；能分開就分開 branch。**

判準不是「檔案數」，是**能不能獨立 revert**：

| 情況 | 分不分 |
|---|---|
| 两個決議互不相依，各自有獨立的「為什麼」 | **分開**（各自一個分支＋一個 commit） |
| 「加功能」＋「補這個功能的測試」 | **不分**——沒有測試那個功能不成立，兩者是同一件事 |
| 「寫腳本」＋「補 `.gitignore` 排除腳本產生的暫存檔」 | **分開**——第二個改動即使沒有第一個也站得住 |

實例：同一次任務裡回饋兩個不相關的規範決議（一個是檢查腳本、一個是文件格式的
決議），開了兩個獨立分支＋各自獨立 commit，即使兩者「表面上都是回饋給同一個
skill」。理由：之後只想 revert 其中一個時不會牽連另一個。

## Git identity：不動 config，一次性帶入

即使缺身分導致 `git commit` 失敗，**都不要**修改 git config（local 或 global,
都算）——這是先於本 skill 就存在的鐵則，不因為「只是為了能 commit」就破例。

用 `-c` 對單次指令帶入身分，不落地成任何設定檔：

```bash
git -c user.name="..." -c user.email="..." commit -m "..."
```

身分來源優先順序：

1. 這個 workspace 裡其他 repo 已經在用的身分（`git config user.name`／`user.email`
   在別的 repo 查得到就沿用，同一個人做的事沒理由用不同身分）
2. 查不到就問，不要自己編一個

## Submodule：當它是一個完整的、獨立的 repo

Submodule 不是「主 repo 的一部分」，是一個有自己 remote、自己 `main`、
自己歷史的獨立 repo。所有規則原樣套用一次：

- **它的 `main` 一樣受禁令 1 保護**——不能直接 commit 上去，開自己的分支
- **改動性質不同時，它裡面也要分開分支**（上面那條規則對它同樣成立）
- **先確認它是不是使用者能控制的 repo**：`git -C <submodule> remote -v` 查 owner。
  使用者自己的 repo（即使是拉來當 submodule 用）可以在自己的分支上動；
  真正的第三方模板/套件不要碰——這是禁令 5「不改上游/第三方套件」的判準所在，
  兩種外觀上都是「submodule」，區別只能從 remote owner 查出來

### 主 repo 看到 submodule 變成 dirty 時

在 submodule 裡開分支、commit 之後，主 repo 的 `git status` 會顯示
`M <submodule目錄>`（gitlink 指標跟主 repo 記錄的 commit 不一致）。

**這是預期行為，不是錯誤**，但兩件事不要做：

1. **不要順手 `git add <submodule目錄>` 把新 commit 釘進主 repo**——除非那個
   submodule commit 已經 push 且合併進它自己的 `main`。釘一個還在本機分支、
   隨時可能被 rebase／消失的 commit，主 repo 記錄的就是一個不穩定的參照
2. **不要放著不解釋**——在當次任務的紀錄裡寫清楚：submodule 現在多了哪些分支
   ／commit、為什麼主 repo 沒有跟著更新 pin、之後要怎麼推進（等 PR 合併後
   `git submodule update --remote`）

## Push 與 PR

### 每次都要確認，不要沿用上一次的授權

「上一次類似的操作使用者同意過」**不等於**「這一次也同意」——尤其是
push／開 PR 這類外部可見的動作。同一個任務裡，使用者對同一件事**可能在不同
時間點給出不同答案**（例如先說「不開 PR，只留 commit」，之後又主動要求
「幫我發 PR」）。每次都當作新的一次問，不要因為「反正之前問過同類的」就跳過。

### 分支對應 PR：不合併不相關的分支

同前面「分支與 commit」的判準——兩個不相關的分支，開兩個獨立 PR，
不要為了省事合併成一個。review／revert 的顆粒度要跟改動的顆粒度一致。

### 動手前先確認做得到，做不到就直接說

承諾「幫你發 PR」之前，先檢查有沒有實際推的能力：

```bash
gh auth status
which ssh
env | grep -iE "GH_TOKEN|GITHUB_TOKEN"
```

三者都沒有，就是真的做不到——**直接說清楚環境缺什麼**，不要嘗試繞過
（不要在對話裡跟使用者要 token／密碼，憑證不進對話,理由與禁令 4「不 commit
機密」同源：一旦讓憑證出現在對話或任何非受控管道，就製造了洩漏面）。

**做不到時檢查有沒有替代路徑，而不是卡在原地**：容器化環境常見的替代路徑是
「這個目錄本身是從主機掛進來的」——檢查 `mount` 或 compose 檔的 `volumes`
設定，如果是 bind mount，代表容器裡做的 commit **已經真實存在於主機的檔案
系統**，使用者可以直接在主機端、用他自己已經設定好的憑證完成 push，
不需要在容器裡想辦法生出一套新的認證。

## 收尾檢查（每次「完成一個任務」前）

- [ ] 這次有沒有跨到別的 repo（submodule）？跨的話，那邊的分支狀態乾淨嗎
      （commit 訊息清楚、沒有 `__pycache__` 之類的產物殘留）
- [ ] 主 repo 顯示 submodule 為 dirty 時，紀錄裡有沒有寫清楚原因跟現況
- [ ] Push／PR 的決定（做了／沒做／為什麼）有沒有寫進任務檔，不是只留在對話裡——
      對話會被 compact，任務檔不會
