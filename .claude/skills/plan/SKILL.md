# 規劃任務

`CLAUDE.md` 已定義動手前四步與強度分級。本 skill 是它們的展開。

---

## 第 1 步：回述

一兩句講清理解，**必須包含「不包含什麼」**：

> 我理解你要的是把訂單查詢從 8 秒降到 2 秒內。範圍包含查詢邏輯與索引，
> **不包含** API 回傳格式與前端。

沒有「不包含」的回述沒有用 —— 範圍膨脹都是從沒講清邊界開始的。

委託方沒給驗收標準時，這一步要把它問出來或提出來：

> 驗收我提議是「用正式環境資料量，同一組條件跑 5 次都在 2 秒內」，可以嗎？

---

## 第 2 步：定位

**實際找出目標在哪，附證據。禁止用猜的檔名開始工作。**

兩件事都要做：

1. **找到程式碼**：列出檔案與行號
2. **回查事故紀錄**：用檔名／功能名 grep 一次
   ```bash
   grep -n "export_handler" docs/KNOWN-ISSUES.md
   ```
   **有命中就要在計畫裡寫明怎麼避開。** 這一步是「修 A 壞 B」的主要防線 ——
   跳過它，前人記錄的坑就白記了。

定位不到目標時，**說出來並問**，不要挑一個最像的開始改。

---

## 第 3 步：講計畫

### 先判強度

| 強度 | 情況 | 產出 |
|---|---|---|
| **L0** | 錯字、註解、格式 | 不需要計畫檔 |
| **L1** | 單一模組的 bug 修復、小功能 | 不需要計畫檔，但回報要完整 |
| **L2** | 跨檔／跨模組、牽動 3+ 檔 | **一份 `docs/tasks/YYYY-MM-DD-<slug>.md`** |
| **L3** | 架構改動、影響全部模組或使用者可見行為 | **展開成資料夾**（見文末） |

不確定就往高一級，**但要說出理由**。把 L1 的事套上 L3 流程是浪費。

### 計畫檔骨架（L2 預設）

位置：`docs/tasks/YYYY-MM-DD-<slug>.md`

日期前綴的理由：避免撞名、天然按時間排序、回查時通常記得「大概什麼時候做的」。
**完成後不刪不移動** —— 按時間讀 `docs/tasks/` 是新人了解專案演進最快的方式。

```markdown
# <任務名>

狀態：進行中 / 已完成 / 已放棄
強度：L2
日期：YYYY-MM-DD

## 目標
<要達成什麼，不是要改哪個檔案>

## 範圍
包含：
不包含：

## 驗收
<怎麼算做好了。可觀察、可重複>

## 假設（若不對請說）
- <一行一條 + 理由>

## 變更清單
| 檔案 | 變更性質 |
|---|---|

## 驗證步驟
- [ ] <寫實際要跑什麼指令>

## 回退方式
<怎麼還原。L2 以上一定要寫>

## 完成紀錄
| 日期 | 項目 | commit | 驗證結果（實際觀察到什麼） |
|---|---|---|---|

## 問題紀錄
| 日期 | 問題 | 根因 | 處理 | 已升級到 KNOWN-ISSUES？ |
|---|---|---|---|---|
```

前四節（目標／範圍／驗收／假設）直接沿用委託時的四欄位 ——
**計畫是委託的延續，不是另一份東西**。

### 建完計畫檔要做的

- 在 `docs/tasks/README.md` 的索引表加一列（日期／任務／涉及範圍／一句話）
- **等同意才動手**（L2 以上）

## 第 4 步：缺口分類

需求文件永遠有沒寫到的細節，這正常。分兩類處理：

### 阻斷型 → 問，最多 3 個

判準：**不同的解讀會白做或不安全。**

- 這個 API 給誰用（決定要不要驗證身份）
- 要不要相容既有欄位／端點
- 資料量級（決定架構）
- 失敗時該重試、回錯誤、還是略過

超過 3 個 → **把「需求不足」當成結論回報**，不要丟一串問題回去。

### 非阻斷型 → 自己選，寫成假設清單

判準：**任何合理選擇都能用，錯了改起來便宜。**

一行一條、附理由、標明「若不對請說」：

```
假設（若不對請說，改起來便宜）
- 錯誤回應用 { error: { code, message } }，因為需求文件的範例是這個形狀
- 時間欄位一律 ISO 8601 UTC，因為需求沒指定時區
- 分頁用 offset/limit，因為沒有游標需求的描述
```

三個要求：

1. **假設要寫進交付物**（計畫檔 + 關鍵處的程式碼註解），不能只在對話裡
2. **假設被推翻時要記一則 KNOWN-ISSUES**，不要默默改掉 —— 「當初為什麼這樣假設」對下次判斷有用
3. **假設清單不是免責聲明**。判準就是那句：錯了會不會白做

---

## 兩種任務主線的差異

| | 擴充／修改既有 | 新建 |
|---|---|---|
| 最大風險 | 改 A 壞 B | 蓋出不是對方要的東西 |
| 定位階段多做 | **先復現現況**並把輸出留在計畫檔 | 需求缺口分類（上方第 4 步） |
| 技術選擇 | 沿用既有慣例，不引進個人偏好 | **必須在計畫階段講出來並取得同意**（框架、目錄結構、測試方式） |
| 中途 | 每步確認未破壞既有行為 | **最小可跑骨架先給對方看**，再長內容 |
| 驗證重點 | 回歸：原本能做的還能做 | 對照需求逐條驗收 |

### 「先復現現況」是什麼意思

改之前跑一次，把**實際輸出**貼進計畫檔。改完跑同一組輸入。兩份都留。

沒有這個，「改好了」無法證明 —— 也無法發現你修的是一個本來沒壞的東西。

復現不出來 → 寫「無法復現」並問，不要假設症狀存在然後開始改。

## L3：展開成資料夾

判準：**需要分階段，且每階段可獨立出貨。**

一個階段必須同時滿足三件事，不滿足就不是階段，是待辦清單裡的一行：

1. **可獨立出貨** —— 停在這裡系統是自洽的
2. **可驗證** —— 有明確、可觀察的完成判準
3. **可回退** —— 知道怎麼退，且退回後系統仍自洽

```
docs/tasks/YYYY-MM-DD-<slug>/
├── README.md          總覽：目標、階段索引與狀態總表、依賴關係
├── DECISIONS.md       待決事項與決議紀錄
├── EXECUTION-LOG.md   跨階段完成紀錄
└── phase-N-*.md       每階段一份（骨架同上方 L2 計畫檔）
```

排序原則：

- **止血優先** —— 與目標無關但已上膛的地雷先拆
- **基線在改動之前** —— 沒有回歸測試就動手，等於每一步都無法驗證
- **風險遞增** —— 不改變外部行為的排前面
- **會改介面／命名的排最後**，並且獨立分支與獨立 MR

**試點再推廣**：要改 N 個地方時，先在 1 個地方做完並驗證。挑**最單純的**當試點，
不要挑最複雜的 —— 你會同時在解兩個問題。

**每階段結束（或中途卡住）都要回寫**完成紀錄與問題紀錄，並同步 README 狀態總表。
卡住的原因是下一輪最需要的資訊。

⚠️ 回寫時 **checklist 與完成紀錄要一起更新**。常見失誤：完成紀錄寫了，
但同一份文件上方的驗證清單還標「未做」，兩處矛盾，讀的人不知道信哪一個。
