# 規劃任務

`CLAUDE.md` 已定義動手前四步與強度分級。本 skill 是它們的展開。

---

## 第 0 步：判斷要不要走計畫流程

**以下五條全部成立** → 直接做（做完仍須回報）：

1. 在交辦範圍內 —— 不是順手發現的
2. 除委託明確要求的變化外，**對外行為零變化**
3. 不動介面、依賴、權限、機密、資料
4. 能立刻驗證
5. **atomic revert** —— 單一 commit 可還原，無外部副作用

**任一條不成立** → 走下面四步，先講計畫等同意。

### 範圍外發現的問題

判準是它會不會擋住這次的 Definition of Done，以及**修它要付多少**：

| 情況 | 動作 |
|---|---|
| 不擋 DoD | **只記錄，不動手** —— 順手修下去就是 scope creep |
| 擋住 DoD，且修它在原範圍內（小、可控、可獨立驗證）| 修，並在回報明說「這不在原委託內，但不修無法驗收」 |
| 擋住 DoD，但修它會顯著擴大範圍或動到別的介面 | **停下來說明並等指示** —— 「有東西擋住驗收」本身就是需要人決策的資訊 |

第二列與第三列的界線由**代價**決定，不由「是不是範圍外」決定 ——
範圍外只是必要條件。不確定屬於哪一列時，走第三列。

## 第 1 步：scope definition

一兩句講清理解，**必須包含 out of scope**：

```
我理解你要的是 <目標，用可觀察的結果描述>。
範圍包含 <會動到的部分>，不包含 <明確排除的部分>。
```

沒有 out of scope 的回述沒有用 —— 範圍膨脹都是從沒講清邊界開始的。

委託方沒給驗收標準時，這一步要把它提出來，不要自己假設：

```
驗收我提議是 <可觀察、可重複的判準>，可以嗎？
```

---

## 第 2 步：locate

**實際找出目標在哪，附證據。禁止用猜的檔名開始工作。**

1. **找到程式碼**：列出檔案與行號
2. **回查事故紀錄**：用檔名／功能名 grep `docs/KNOWN-ISSUES.md`（做法見 `record` §1）。
   **有命中就要在計畫裡寫明怎麼避開** —— 這是「修 A 壞 B」的主要防線

定位不到目標時**說出來並問**，不要挑一個最像的開始改。

---

## 第 3 步：講計畫

### Effort sizing

| 強度 | 情況 | 產出 |
|---|---|---|
| **L0** | 錯字、註解、格式 | 不需要計畫檔 |
| **L1** | 單一模組的 bug fix、小功能 | 不需要計畫檔，但回報要完整 |
| **L2** | 跨檔／跨模組、牽動 3+ 檔 | **一份 `docs/tasks/YYYY-MM-DD-<slug>.md`** |
| **L3** | 架構改動、影響全部模組或使用者可見行為 | **展開成資料夾**（見文末）|

不確定就往高一級，**但要說出理由**。把 L1 的事套上 L3 流程是浪費。

### 計畫檔骨架（L2 預設）

位置：`docs/tasks/YYYY-MM-DD-<slug>.md`。日期前綴避免撞名、天然按時間排序。
**完成後不刪不移動** —— 按時間讀 `docs/tasks/` 是了解專案演進最快的方式。

```markdown
# <任務名>

狀態：進行中 / 已完成 / 已放棄
強度：L2
日期：YYYY-MM-DD

## 目標
<要達成什麼，不是要改哪個檔案>

## 範圍
包含：
不包含：

## 驗收
<怎麼算做好了。可觀察、可重複>

## 假設（若不對請說）
- <一行一條 + 理由>

## 變更清單
| ID | 檔案 | 變更性質 |
|---|---|---|

## 驗證步驟
- [ ] <寫實際要跑什麼指令>

## 回退方式
<怎麼還原。L2 以上一定要寫>

## 完成紀錄
| 日期 | 項目 | commit | 驗證結果（實際觀察到什麼） |
|---|---|---|---|

## 問題紀錄
| 日期 | 問題 | 根因 | 處理 | 已升級到 KNOWN-ISSUES？ |
|---|---|---|---|---|
```

前四節（目標／範圍／驗收／假設）直接沿用委託時的四欄位 ——
**計畫是委託的延續，不是另一份東西**。

變更清單的 `ID` 只需檔內唯一（`C1`、`C2`…），之後可直接指涉「C3」不用重述。
**只在 L2 以上用**（理由見 `docs/DECISIONS.md` D9）。

建完計畫檔要：在 `docs/tasks/README.md` 索引表加一列，然後**等同意才動手**（L2 以上）。

## 第 4 步：requirement gap triage

需求永遠有沒寫到的細節，這正常。分兩類：

### Blocking → 問，最多 3 個

判準：**不同的解讀會白做或不安全。**
（給誰用／要不要相容既有介面／資料量級／失敗時重試或略過）

超過 3 個 → **把「需求不足」當成結論回報**，不要丟一串問題回去。

### Non-blocking → 自己決，寫成 assumptions

判準：**任何合理選擇都能用，錯了改起來便宜。**
一行一條、附理由、標明「若不對請說」。

三個要求：

1. **假設要寫進交付物**（計畫檔 + 關鍵處的註解），不能只在對話裡
2. **假設被推翻時要記一則 KNOWN-ISSUES**，不要默默改掉 ——
   「當初為什麼這樣假設」對下次判斷有用
3. **假設清單不是免責聲明**。判準就是那句：錯了會不會白做

## 設計一個「選用」機制時：沒有預設路徑，就要有失敗時的輸出

留了選用機制但沒把它做成預設路徑，實務上等於**預設關閉** ——
啟用門檻越高（要同時記住幾個參數、要改別的檔案），越接近沒有這個機制。

真正的代價不在「沒啟用」，在**沒啟用時的失敗長什麼樣**：

| | 失敗時有明確輸出 | 沒有任何輸出 |
|---|---|---|
| 使用者的解讀 | 「我少帶了一個參數」 | **「整個環境壞了」** |
| 後續動作 | 補上參數 | 據此改變工作方向，錯誤往外擴散 |

所以兩件事至少要成立一件：**把它做成預設路徑**，或**失敗時明講**。
明講的話**成功也要印一行** —— 否則「沒印」和「還沒跑到那裡」分不出來。
兩者都缺時，使用者一定會用最壞的解釋去填那個空白，而那個解釋會擴散。

## 兩種任務主線

| | 擴充／修改既有 | 新建 |
|---|---|---|
| 最大風險 | 改 A 壞 B | 蓋出不是對方要的東西 |
| locate 階段多做 | **reproduce baseline**（見下）| requirement gap triage |
| 技術選擇 | 沿用既有 convention，不引進個人偏好 | **必須在計畫階段講出來並取得同意** |
| 元件邊界 | 沿用既有切法 | 判準見 `docs/DECISIONS.md` D5：看**變更的理由**不是相似度，**先重複，第三次出現再抽** |
| 中途 | 每步確認未破壞既有行為 | **最小可跑骨架先給對方看**，再長內容 |
| 驗證重點 | regression：原本能做的還能做 | 對照需求逐條驗收 |

### Reproduce baseline

改之前跑一次，把**實際輸出**貼進計畫檔。改完跑同一組輸入。兩份都留。

沒有這個，「改好了」無法證明 —— 也無法發現你修的是一個本來沒壞的東西。
復現不出來 → 寫「無法復現」並問，不要假設症狀存在然後開始改。

## L3：展開成資料夾

判準：**需要分 phase，且每個 phase 可獨立出貨。**

一個 phase 必須同時滿足三件事，不滿足就不是 phase，是待辦清單裡的一行：

1. **independently shippable** —— 停在這裡系統是自洽的
2. **可驗證** —— 有明確、可觀察的完成判準
3. **可回退** —— 知道怎麼退，且退回後系統仍自洽

```
docs/tasks/YYYY-MM-DD-<slug>/
├── README.md          總覽：目標、phase 索引與狀態總表、依賴關係
├── DECISIONS.md       待決事項與決議紀錄
├── EXECUTION-LOG.md   跨 phase 完成紀錄
└── phase-N-*.md       每個 phase 一份（骨架同上方 L2 計畫檔）
```

排序原則：

- **止血優先** —— 與目標無關但已上膛的地雷先拆
- **baseline 在改動之前** —— 沒有 regression 測試就動手，等於每一步都無法驗證
- **風險遞增** —— 不改變外部行為的排前面
- **會改介面／命名的排最後**，並且獨立分支與獨立 PR

**Pilot 再推廣**：要改 N 個地方時，先在 1 個地方做完並驗證。
挑**最單純的**當 pilot，不要挑最複雜的 —— 你會同時在解兩個問題。

**每個 phase 結束（或中途卡住）都要回寫**完成紀錄與問題紀錄，並同步 README 狀態總表。
卡住的原因是下一輪最需要的資訊。

⚠️ 回寫時 **checklist 與完成紀錄要一起更新**。常見失誤：完成紀錄寫了，
但同一份文件上方的驗證清單還標「未做」，兩處矛盾，讀的人不知道信哪一個。
