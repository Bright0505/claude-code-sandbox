# 陷阱

本 skill 不是禁令也不是流程，是**診斷心態**——收集真實踩過的案例，
教怎麼在下結論前多問一句「這個異常真的是我以為的那個意思嗎」。

---

## 第一個失敗訊息不代表整條路都斷了

沒有 `ssh` client 導致 `git fetch`／`push` 全部失敗（`cannot run ssh: No such
file or directory`），很容易直接推論成「這個環境完全連不上 GitHub」。

實際上只有 **SSH transport** 壞了。同一個公開 repo，換成 **HTTPS transport**
（`git fetch https://...`、`git ls-remote https://...`）完全不需要認證，一樣
能用——只有 **push（寫）** 才會卡在認證，**fetch（讀）對公開 repo 不需要**。

**判準**：一個操作失敗時，先問「壞的是這條路徑，還是整個目的地不可達」。
換一種 transport／換一種工具快速驗證一次，成本通常很低，不要把單一失敗
直接推論成「整體都不可能」。

---

## 空輸出／零結果不等於「確認是零」

GitHub API 查 `?state=open` 回空——這個空 list 有兩種可能：真的沒有 open
的 PR，**或者**查詢參數本身不對（PR 早就是 `closed`／`merged`，用
`state=open` 篩不到）。改用 `state=all` 並確認 HTTP 狀態碼是 `200`，
才能分辨「確認結果是零」跟「查詢方式錯了看起來像零」。

這跟 D7 腳本的「條目數斷言」是同一個道理：**靜默的零結果是最危險的失效
模式**，因為它長得跟「乾淨通過」一模一樣。看到一個查詢/檢查回報零結果，
先確認查詢本身有沒有跑對（換個已知有結果的參數測一次），再把「零」寫進結論。

## 環境層的錯誤訊息，先分類再下結論

寫檔案得到 `EROFS: read-only file system`——不是內容或權限問題，是**掛載
層級**的限制。這類系統層錯誤（`EROFS`／`ENOSPC`／沙盒相關訊息）先用
`mount`／`df` 之類的工具確認範圍（整個檔案系統唯讀，還是只有這個子目錄），
再決定要不要換位置，不要對同一個操作重試。

實例：`scripts/` 唯讀是刻意的沙盒防護（保護 `entrypoint.sh`／
`init-firewall.sh`），查出範圍後才知道要換到 `tools/`，不是要修的 bug、
也不是要繞過的障礙。

`git commit` 失敗說「Author identity unknown」——不是程式碼問題，是這個
repo（或 submodule）第一次在這個環境裡被寫入，沒繼承任何身分設定。這類
「操作前置條件缺失」的訊息通常會**直接告訴你缺什麼**，照著訊息的診斷走，
但不一定要照訊息建議的修復手法走——它可能建議 `--global`，但那違反
「不動 git config」的規則，改用 `-c` 一次性帶入。

## 系統提示「某檔案被使用者或 linter 改動」不一定是外部事件

Harness 偵測到檔案內容變化時會發出提醒，但變化的來源不只有「有人真的改
了它」——**切換 git 分支本身就會讓工作目錄的檔案內容改變**（新分支的
tracked 版本跟舊分支不同，這是 `git checkout`／`git merge` 的正常行為）。

收到這類提醒時，先檢查最近有沒有跑過分支切換相關指令。有的話，內容差異
很可能就是切換的自然結果，不是真的有人在背後動了檔案——不要因此去猜
「使用者是不是改了什麼我不知道的東西」。

---

## 一次執行多個指令、輸出混在一起時，反直覺的命中不能直接信

在單次呼叫裡並排跑多個 `grep`／`find`（用 `;` 或換行分隔），如果指令之間
沒有清楚的輸出分隔標記，很容易把「上一個指令的殘留輸出」誤讀成「這個指令
的結果」。

實例：一次查了好幾個模式，其中一個 `grep` 看起來命中了一堆跟目標完全無關
的第三方檔案——重新用單獨、乾淨的一次 `grep` 對其中一個檔案覆驗，結果是
空的，證明原本那批「命中」是輸出混雜造成的誤讀，不是真的匹配。

**看到反直覺的結果，先用最小、最乾淨的一次指令覆驗，再寫進結論**——
這跟「一手來源優於二手」（見 `verify` skill）是同一個原則，只是這裡的
「二手來源」是自己剛剛跑的、可能被污染的輸出。
