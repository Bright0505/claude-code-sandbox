# 發佈

這個 repo 同時是兩樣東西：一套要給別人用的**產品**（sandbox 執行環境 + 開發規範），
以及**這套規範自己的驗證樣本** —— 樣本數不足時拿自己當樣本。

**發佈的是產品，不是產品的研發紀錄。**

研發紀錄**不銷毀**（禁令 8）—— 留在發佈 tag 之前的 git 歷史。發佈這個動作做的是
「不出現在發佈樹裡」，不是「消失」。兩者的差別要在文件上看得出來，否則下一輪
會有人以為紀錄被刪了，重新調查同一件事。

⚠️ 本 skill 只在**上游自己發佈**時使用。

---

## 1. 開始清理前：先確定骨架的邊界

不要一份一份憑感覺判斷。先把發佈樹分成三種形態，再逐檔歸類：

| 形態 | 意思 | 收尾狀態 |
|---|---|---|
| **產品本體** | 套用端真的要用的東西 | 原樣出貨 |
| **空骨架** | 結構要在、內容屬於套用端 | 只留表頭、格式說明、空表格 |
| **上游自己的紀錄** | 我們拿自己當樣本留下的痕跡 | 不出貨（留在 git 歷史） |

歸類的判準只有一條：

> **套用端讀到它，會不會以為那是自己 repo 發生過的事？**
>
> 會 → 不出貨，或降為空骨架。
> 不會（它講的是格式、是產品的能力邊界、是套用端會遇到的坑）→ 出貨。

**空骨架不是空檔案。** 一份空骨架必須自帶兩樣東西，否則接手的人不知道它為什麼存在：

1. 這裡該放什麼、格式在哪裡（指向對應的 skill）
2. 上游原本的內容去哪了、怎麼取回（見 §7 —— 產物端沒有 git 歷史）

---

## 2. 移除任何紀錄前：先確認判準有沒有載體

**順序不可反。** 對每一則要移除的內容逐條問：

| 這一條的判準 | 動作 |
|---|---|
| 已經在 skill／`README`／`CHANGELOG` 裡 | 可移除 |
| 只活在這份紀錄裡 | **先升級進 skill，才移除** |
| 純粹是某一次的診斷過程，抽不出判準 | 移除，不留 —— 硬塞只會製造檢索雜訊 |

⚠️ **升級與移除要切成兩個 commit。** 同一個 commit 的話，revert 掉「移除」會把
規則一起撤掉 —— 而且從 diff 上分不出哪些是規則、哪些是痕跡。

**最容易失去載體的是回報格式的 `沒做什麼`** —— 它的內容 diff 和 git log 都沒有，
紀錄一移除就整段消失。移除前把它搬進 `CHANGELOG.md` 的「已知未驗」。

---

## 3. 移除紀錄時：引用審計要分兩類

grep 到的引用**不是同一種東西**，混在一起數就會判斷錯：

| 類型 | 形態 | 移除後 |
|---|---|---|
| **前瞻規則** | 指向**目錄或檔名格式**（`docs/tasks/YYYY-MM-DD-*.md`）| 不受影響 —— 那是給套用端的規則 |
| **指名引用** | 指向**特定檔名或條目 ID**（`K-<n>`／`D<n>`）| 會斷，每一處都要處理 |

```bash
grep -rnE "docs/(DECISIONS|KNOWN-ISSUES|tasks)|\bK-[0-9]+\b|\bD[0-9]+\b" \
    .claude/ CLAUDE.md README.md ONBOARDING.md CHANGELOG.md docs/
```

**每一筆都要能說出它屬於哪一類。** 說不出來的就是還沒審完 —— 不要用「看起來沒事」結案。

---

## 4. 只保留一部分條目時：ID 不重編，關聯改寫為形態

移除一部分條目會讓留下來的條目 `關聯` 指向死 ID。結構檢查腳本會紅
（它從 `關聯` 抽 ID 檢查存在性），這是**好事** —— 它擋住了一份表面正常的紀錄。

- ID **永不重用**（`record` §3），不因為移除而重編
- 死掉的 `關聯` 改寫成**形態描述**，並把**形態名稱留下來**當之後建立關聯的錨
  （`record` §6 規則 6：跨專案共用的文件不引用專案專屬 ID）
- 檔頭註明上游用到第幾號、**套用端從下一號接續**，否則兩邊的編號會撞在一起

**代價要寫出來**：可 grep 的連結消失了，只剩形態名稱（`record` §7 硬規則 ①）。
不寫的話，下一個人會以為那個形態從來沒復發過。

---

## 5. 出貨前：洩漏面掃描

骨架不能帶走上游的環境。發佈樹裡不該出現：

| 類 | 形態 |
|---|---|
| 專案名／服務名 | 其他專案的容器名、compose service 名 |
| 網路拓撲 | 內網網段、port、network 名 |
| 主機路徑 | 家目錄、掛載點 |
| 憑證與個資 | token、真實 email（禁令 4）|

寫成一次執行、輸出命中表（`verify` §6），不要一個字串問一次。

⚠️ **零命中不等於乾淨** —— 它只證明「你想到的那幾個字串不在」，這正是
`record` §6 規則 5 的形態（宣稱「內容無損」時 grep 只能當輔助）。
無法列舉的部分要換角度：**把發佈樹裡的 `docs/` 整份讀一遍**，最好換一個 agent 讀。

---

## 6. 版號與 CHANGELOG：語意只放一份

版號語意寫在 `CHANGELOG.md`，其他地方只放連結。**兩份一定會漂移。**

每次發佈，`CHANGELOG.md` 至少要有：

- **改了什麼** —— 只寫套用端需要知道的；內部重構與錯字不列
- **移除了什麼** —— 附取回的方式（見 §7）
- **已知未驗** —— §2 搬過來的 `沒做什麼`。**這一節不可省**，它是那些內容唯一的載體

**每個版本的區塊要有長度上限**（十幾行），否則發到第五版它就沒人讀了 ——
而沒人讀的變更紀錄等於沒有變更紀錄。壓縮的方法不是刪內容，是**把不隨版本變的東西
抽成檔尾的固定小節**（紀錄去哪了、怎麼取回、散佈管道的限制）。
自檢訊號：**兩個版本的區塊裡出現同一段話** —— 那段話不屬於任何一個版本。

## 7. 決定散佈管道時：tag 管不到內容乾淨度

GitHub Template repository 只複製 **default branch 的 HEAD**，而且
**產物沒有 commit 歷史、沒有 tag**，也不能指定要從哪個 ref 複製。所以：

| 管道 | 拿到什麼 | 有歷史嗎 |
|---|---|---|
| Template repository | default branch 的 HEAD | **沒有** |
| submodule 釘 tag | 該 tag | 有 |
| `git clone --depth 1 --branch <tag>` 快照 | 該 tag | 沒有（`--depth 1`）|

兩個推論：

1. **`main` 的 HEAD 就是出貨物。** 乾淨度是 `main` 的責任，tag 給不了 ——
   「先打 tag，之後從 tag 複製就乾淨了」沒有因果關係
2. **任何寫「見 git 歷史」的指針，在 template 產物裡是死的。** 要能取回的話，
   指令要帶上游 repo 的位址，不能只寫 `git log`

---

## 8. 發佈到 `main`：搬檔案，不合併分支

**`main` 是衍生物，不是分支。** 上游的工作樹在 `dev`，`main` 上每一個檔案都從 `dev` 產生。

| | `dev` | `main` |
|---|---|---|
| 產品檔 | 一直在改 | 每次發佈取一份 |
| 紀錄（任務檔／事故／決議）| **持續累積** | 只有空骨架 |
| 骨架的來源 | `release/skeleton/` | — |
| git 歷史 | 真正的開發史 | 每次發佈一個 commit |
| tag | 不打 | 打在這裡 |

兩條規則，缺一條這套就不成立：

1. **兩邊從不 merge。** 走 merge 的話 `docs/` 每次都會衝突，要靠一個記得執行的
   動作去擋 —— 那就是一個會被忘記的步驟
2. **`main` 上禁止手改。** 一改就製造了「只存在於 `main`」的內容，
   下次發佈會**靜默覆蓋**掉它

發佈本身也不直接 commit 到 `main`（禁令 1）—— 從 `main` 開一支發佈分支、
在那裡把內容擺好、走 PR 進 `main`，tag 打在 merge 之後。
好處不只是合規：**發佈的 diff 變成可 review 的東西**，包括腳本移除了哪些非骨架檔案。

紀錄之所以不出現在 `main`，不是因為發佈時清掉了，而是**它從來不在產品檔清單裡**。
「不會被搬過去」比「記得要清掉」強一個量級（見 `plan` skill「設計一個「選用」機制時」那一節）。

### 三個會靜默出錯的地方

| 陷阱 | 症狀 | 守衛 |
|---|---|---|
| `git checkout <ref> -- <路徑>` **不傳遞刪除** | 對方已移除的檔案永遠留在這邊，而且 diff 看不出來 | 先用同一份清單 `git rm -rq --ignore-unmatch` |
| pathspec 打錯 → `git diff` 回空 | **「沒漂移」和「沒比到東西」長得一樣** | 先用 `git ls-tree` 確認匹配數 > 0 |
| 某些 shell 不做 word splitting | 空白分隔的清單被當成**一個**路徑：`git rm` 報錯、`git diff` 回空，兩個假象同時出現 | 清單用陣列，腳本寫 `#!/bin/bash` |

### 「骨架裡沒有紀錄」要有斷言

發佈流程只覆寫骨架檔，**不會刪掉多出來的檔案**。沒有斷言的話，
這件事只能靠紀律，而回答「保證沒有紀錄嗎」只能說「照規矩做就沒有」。至少斷言兩件事：

- 發佈端 `docs/` 的檔案清單**完全等於**預期的那幾個（多一個就中止）
- 骨架裡 `^### K-` 與 `^## D` 的命中數為零

---

## 9. 發佈後：從產物端驗收，不從原始碼端

在原始碼端讀起來合理的東西，在產物端可能指向不存在的檔案。**驗收要換一端做**：

- [ ] 真的產生一份（`gh repo create --template`，或 tag 快照）
- [ ] `.claude/skills/` 載得到嗎 —— 問一句話驗（讓它說出常駐的禁令），
      **不要只確認檔案在**。載不到的話，套用端拿到的是一份指向不存在 skill 的 `CLAUDE.md`
- [ ] 骨架檔案裡的每個指針，在產物端還指得到嗎（含 §7 的歷史指針）
- [ ] 空骨架有沒有告訴接手的人「這裡該放什麼」

---

## 收尾

- [ ] 規則升級與紀錄移除是**兩個 commit** 嗎
- [ ] 每一則被移除的紀錄，它的 `沒做什麼` 有載體嗎
- [ ] 洩漏面的「零命中」有第二個角度佐證嗎（§5 —— grep 不算完整證據）
- [ ] 驗收是在**產物端**做的嗎
- [ ] tag 打在 merge 之後的 `main` 上，而且沒有自動 push 嗎（禁令 1-2）
