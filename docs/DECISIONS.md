格式與規則見 `.claude/skills/record/SKILL.md`。

## D1 — KNOWN-ISSUES 的歸檔邏輯（**待決**）

**問題**：`docs/KNOWN-ISSUES.md` 會無限成長。歸檔可以控制大小，但歸檔是
**唯一會讓紀錄變難找的操作** —— 做壞了會直接摧毀它最主要的用途（開工前回查，
避免「修 A 壞 B」）。

### 已定案的部分（已寫進 `record` skill）

| 項目 | 決議 |
|---|---|
| 資格 | 狀態為 `已修`／`已推翻`／`已被架構改動消滅`，且 `守備` 非空且該測試存在並為綠，且關聯鏈上無 `已知未修` |
| 永不歸檔 | `已知未修`、`未處理`、`已修（無守備）` |
| 主檔留 stub | **必須**，且 stub 要含「影響範圍」關鍵字，否則 `grep` 失效 → 有人以為沒歷史 → 重踩 |
| 搬移非刪除 | 明細完整搬走，一個字不刪；archive 進版控；ID 永不重用 |
| 關聯群組原子性 | 同一關聯鏈要嘛一起歸檔要嘛都不動 |
| 觸發方式 | **手動**（自動化容易誤埋，且目前經驗不足以定規則） |
| 歸檔時不做突變驗證 | 太貴且對舊條目做不到。貴的驗證在「修的當下」做，歸檔只檢查證據 + 跑那一個測試 |

### 已被推翻的判定（保留，避免重走）

**「用主檔行數當觸發訊號（例如超過 400 行）」—— 已推翻（2026-08-05）。**

推翻理由（使用者提出）：

1. **行數不等於條目數。** 幾則寫得詳細的條目就能撐過門檻，而檔案其實只有 8 則 ——
   那時候歸檔是純損失。而詳細的條目恰好最有價值，用行數當門檻等於**懲罰寫得好的紀錄**
2. **按大小歸檔會把有關聯的條目切開。** 一則 fix 與前面的 feat 有關聯，
   卻因為湊行數被拆走 → 讓「同一形態復發」看不出來，而那是這個檔案最有價值的功能之一

這個推翻同時導出了「關聯群組原子性」那條規則。

**「每個 commit／每次功能修改都寫一則 KNOWN-ISSUES」—— 已推翻（2026-08-05）。**

推翻理由：會讓 `grep <檔名>` 回一堆雜訊，**檢索價值消失** —— 而檢索正是這個檔案
存在的理由。且 per-commit 的紀錄已經在 git log 裡（commit 訊息本來就要求寫「為什麼」），
再寫一份是重複，重複的兩份一定漂移。

使用者原本的動機是「ISSUES 也是快速了解架構的一種文件」，這個動機成立，
但由另一層滿足更好：**按時間讀 `docs/tasks/` 的計畫檔**（有目標／範圍／假設／變更清單，
比 git log richer），入口是 `docs/tasks/README.md` 的索引表。

### 仍待決

**1. 觸發訊號的具體數值**

目前暫用（未經驗證，憑一次真實 ISSUES 檔案的體感估的）：

- 主檔**有效條目數**超過 ~30 則
- **可歸檔比例**佔有效條目一半以上
- **檢索噪音**：`grep` 一個常見檔名回超過 ~10 筆且多數已修

這三個數字都需要真實使用後校正。

**2. archive 檔的組織方式**

暫定單一 `docs/known-issues-archive.md`，append-only。
不一開始按年份切，是為了避免「這則是 2026 發現還是 2027 歸檔的」這種每次都要想的問題。

**3. ⬅ 使用者保留的討論方向：歸檔的分組是否該對應開發架構**

使用者（2026-08-05）提到歸檔邏輯可能涉及**開發架構的分層概念，例如 Atomic Design**，
希望另開 session 深入討論。

尚未展開的疑問（留給下一輪，不預設答案）：

- 條目要不要按**架構層級**分組（例如 atom／molecule／organism／page，
  或等價的 util／component／feature／app 分層）？
- 若按層級分組，「影響範圍」是否改成層級 + 檔名兩個維度？
- 分層是否能讓歸檔變得更安全 —— 例如「同一層的條目一起歸檔」會不會比
  「同一關聯鏈一起歸檔」更貼近實際的變更耦合？
- 分層會不會讓 `grep` 檢索退化（多一層目錄／多一個維度要記）？
  現行設計刻意用**單一可 grep 的檔案**換取檢索的簡單性，分層要證明它不破壞這一點

**討論這題前建議先讀**：`.claude/skills/record/SKILL.md` 的「歸檔」一節，
以及本條上方的兩則「已被推翻的判定」—— 那兩則解釋了為什麼現行設計看起來
比想像中保守。

**狀態**：**待決**（等真實使用經驗 + 上述架構分層的討論）

## D2 — 規範分成兩份文件（已決議）

**決議**：`ONBOARDING.md`（給人，讀一次）與 `CLAUDE.md`（給 Claude，每輪載入）分開。

**為什麼不是一份**：兩個讀者的需求相反。人讀一次需要名詞解釋與「為什麼」；
Claude 每一輪都載入，所以每行都在付 token。合成一份會同時犧牲兩邊 ——
對人太抽象、對 Claude 太長。

實測：原本單檔 489 行 / 20.5 KB，拆開後常駐部分降到 132 行 / 5.7 KB（−72%）。

**附帶決定**：`CLAUDE.md` 壓在 ~130 行，展開的細節放進 skill 按需載入。
理由是太長的規範會被部分忽略，而被忽略的通常是最具體有用的後半段。

**日期**：2026-08-05

## D3 — 事故紀錄的檔名（已決議：`KNOWN-ISSUES.md`）

**問題**：`ISSUES.md` 會跟 GitLab／GitHub Issues 撞名。新人容易誤讀成「待辦事項」，
但它其實是「踩過的坑」。

**選項**：`ISSUES.md`（已習慣）／`KNOWN-ISSUES.md`／`PITFALLS.md`／`LESSONS.md`

**決議**：`KNOWN-ISSUES.md`。保留熟悉的字，同時消掉「待辦」的誤讀。

**日期**：2026-08-05

## D4 — 事故紀錄用單一 ID 系列（已決議）

**問題**：先前的實務把「執行者自己的失誤」與「被稽核對象的缺陷」分成 `E-n` / `I-n`
兩個系列。

**決議**：單一系列 `K-<n>`。兩系列對讀者是多餘的認知負擔，需要區分時用內容講清楚就好。

**不變的部分**：執行者自己的失誤**仍然要記**（誤報已完成、查錯位置、
弄壞設定檔語法、誤用指令覆蓋檔案），它們對下一輪的價值不低於程式碼缺陷。

**日期**：2026-08-05
