## D1 — KNOWN-ISSUES 的歸檔邏輯（**待決**）

**問題**：`docs/KNOWN-ISSUES.md` 會無限成長。歸檔可以控制大小，但歸檔是
**唯一會讓紀錄變難找的操作** —— 做壞了會直接摧毀它最主要的用途（開工前回查，
避免「修 A 壞 B」）。

### 已定案的部分（已寫進 `record` skill）

| 項目 | 決議 |
|---|---|
| 資格 | 狀態為 `已修`／`已推翻`／`已被架構改動消滅`，且 `守備` 非空且該測試存在並為綠，且關聯鏈上無 `已知未修` |
| 永不歸檔 | `已知未修`、`未處理`、`已修（無守備）` |
| 主檔留 stub | **必須**，且 stub 要含「影響範圍」關鍵字，否則 `grep` 失效 → 有人以為沒歷史 → 重踩（**檔案已被刪除時這條有盲點，見下方「已定案部分的修正」**） |
| 搬移非刪除 | 明細完整搬走，一個字不刪；archive 進版控；ID 永不重用 |
| 關聯群組原子性 | 同一關聯鏈要嘛一起歸檔要嘛都不動 |
| 觸發方式 | **手動**（自動化容易誤埋，且目前經驗不足以定規則） |
| 歸檔時不做突變驗證 | 太貴且對舊條目做不到。貴的驗證在「修的當下」做，歸檔只檢查證據 + 跑那一個測試 |

### 已被推翻的判定（保留，避免重走）

**「用主檔行數當觸發訊號（例如超過 400 行）」—— 已推翻（2026-08-05）。**

推翻理由（使用者提出）：

1. **行數不等於條目數。** 幾則寫得詳細的條目就能撐過門檻，而檔案其實只有 8 則 ——
   那時候歸檔是純損失。而詳細的條目恰好最有價值，用行數當門檻等於**懲罰寫得好的紀錄**
2. **按大小歸檔會把有關聯的條目切開。** 一則 fix 與前面的 feat 有關聯，
   卻因為湊行數被拆走 → 讓「同一形態復發」看不出來，而那是這個檔案最有價值的功能之一

這個推翻同時導出了「關聯群組原子性」那條規則。

### 已定案部分的修正（2026-08-06）

**「stub 要含影響範圍關鍵字」在檔案已被刪除時失效。**

原規則假設 stub 留下的檔名還是個活的檢索鍵。但若那個檔案已經被刪除或改名，
**stub 保留的關鍵字正好指向一個不存在的東西** —— 沒有人會去 grep 一個不存在的檔案。
stub 形式上留了，實質上完全沒有作用，而這是靜默的。

代價極不對稱：

| 誤判 | 後果 |
|---|---|
| **誤歸檔**（形態還在卻當它隨檔案消失） | 坑會被重踩，且重踩時 grep 不到 —— 明細已搬走，stub 的關鍵字又是死的。**stub 這道保險剛好在這個情況失效** |
| **誤保留**（形態真的沒了卻留著） | 主檔多一則雜訊 |

**修正**：

1. **檔案消失 ≠ 形態消失。** 只憑「檔案不在了」不構成歸檔資格；要問的是
   **這個形態在新的實作裡還可能發生嗎**。可能 → 不可歸檔，改為更新 `影響範圍` 指向新位置
2. 當 `影響範圍` 的檔案確實已不存在，**stub 的關鍵字必須改用形態**
   （或形態與舊檔名並列），不能只留死檔名
3. 這個情況的預設**偏向不歸檔**

**為什麼條目在檔案消失後仍有價值**：條目的價值分兩層 —— **定位價值**（grep 得到它）
依賴檔名存在，**判準價值**（下次怎麼提早發現）依賴的是形態、不依賴位置。
而 `record` skill 自己的立場是「`判準` 這一欄是條目的價值所在」，
所以檔案消失後存活的正是承載價值的那一層。真正的損失不是價值消失，是**入口壞了** ——
條目仍然正確卻永遠不會再被讀到，那比刪掉更糟，因為它看起來很健康。
替代入口是**用形態措辭檢索**而非檔名檢索。

**「每個 commit／每次功能修改都寫一則 KNOWN-ISSUES」—— 已推翻（2026-08-05）。**

推翻理由：會讓 `grep <檔名>` 回一堆雜訊，**檢索價值消失** —— 而檢索正是這個檔案
存在的理由。且 per-commit 的紀錄已經在 git log 裡（commit 訊息本來就要求寫「為什麼」），
再寫一份是重複，重複的兩份一定漂移。

使用者原本的動機是「ISSUES 也是快速了解架構的一種文件」，這個動機成立，
但由另一層滿足更好：**按時間讀 `docs/tasks/` 的計畫檔**（有目標／範圍／假設／變更清單，
比 git log richer），入口是 `docs/tasks/README.md` 的索引表。

### 仍待決

**1. 觸發訊號的具體數值**

目前暫用（未經驗證，憑一次真實 ISSUES 檔案的體感估的）：

- 主檔**有效條目數**超過 ~30 則
- **可歸檔比例**佔有效條目一半以上
- **檢索噪音**：`grep` 一個常見檔名回超過 ~10 筆且多數已修

這三個數字都需要真實使用後校正。

**提案（2026-08-06，未決）**：只保留第三條「檢索噪音」，刪掉前兩條。
理由是前兩條都是**大小的代理**，而本條上方推翻行數門檻時已經論證過大小 ≠ 傷害；
第三條測的才是實際傷害（檢索退化了）。這會讓歸檔的觸發從「檔案變大了」
變成「檔案開始妨礙它自己的用途了」，後者才是唯一值得付歸檔風險的理由。
**此提案尚未取得同意，記在這裡避免遺失。**

**2. archive 檔的組織方式**

暫定單一 `docs/known-issues-archive.md`，append-only。
不一開始按年份切，是為了避免「這則是 2026 發現還是 2027 歸檔的」這種每次都要想的問題。

**3. 歸檔的分組是否該對應開發架構 —— 已結案（2026-08-06）**

**原始問題（保留）**：使用者（2026-08-05）提到歸檔邏輯可能涉及**開發架構的分層概念，
例如 Atomic Design**，希望另開 session 深入討論。當時列出四個不預設答案的疑問。

**釐清（2026-08-06）**：Atomic Design 只是舉例。使用者真正關心的是
**新開發時元件的耦合能不能更有彈性、架構能不能更好**，以及
「一個元件被過度共用或過度獨立」該怎麼判斷。

這個釐清同時說明了為什麼它不屬於歸檔：**「元件該怎麼耦合」是新開發時的技術選擇，
跟「舊紀錄怎麼搬」沒有共用的機制。**

**結論：歸檔不引入層級分組。** 原子單位維持「關聯鏈」。層級若要出現，
只能當 `影響範圍` 裡的關鍵字，且**詞彙由各專案自訂 —— 規範不指定分類法**。

當初的四個疑問，逐條回答：

| 疑問 | 回答 |
|---|---|
| 條目要不要按架構層級分組？ | **不要。** 層級是**位置**的屬性，關聯鏈是**形態**的屬性。而會復發的形態通常跨層（跨層正是它危險的原因），按層分組會把鏈切開 —— 那是「按大小歸檔」被推翻的同一個失敗模式換個名字 |
| 影響範圍改成層級 + 檔名兩個維度？ | **不改。** 層級**不穩定且錯了看不出來**：檔名寫錯可偵測（檔案不存在），層級寫錯是靜默錯誤。且每寫一則都要多付一次「這算 molecule 還是 organism」的判斷 |
| 同層一起歸檔會不會比同鏈一起歸檔更貼近變更耦合？ | 只在「整層被重寫」時成立。但那個需求要的是**一個欄位**（用來找出被某次重構消滅的條目），不是一種分組。欄位可查、不搬動任何東西；分組是選一個軸、同時毀掉其他軸 |
| 分層會不會讓 grep 退化？ | 會。而更根本的問題是：Atomic Design 是**前端元件**的分類法，本規範是**專案無關**的（要當 submodule 用在任何專案）。後端／SQL 專案沒有 atom，硬套的結果是留空，而留空的分類欄位就是噪音 |

**這一題導出的新決議**：元件邊界的判準見 **D5**，復發形態當架構訊號見 **D6**。

**狀態**：**待決**（第 1、2 項待真實使用經驗；**第 3 項已結案**）

## D5 — 元件邊界的判準（已決議）

**問題**：新開發時怎麼判斷一個元件是**過度共用**還是**過度獨立**。
由 D1 第 3 項導出（見該條的釐清段）。

**決議：判準是「變更的理由」，不是「程式碼的相似度」。**

兩個地方今天長得一樣、但**因為不同理由而改** → 不該共用，它們的相同是巧合，
共用會把巧合鎖成約束。長得不像、但**永遠必須一起改** → 該共用。
所以「有重複」本身不是訊號，「一起變」才是。

**兩個方向各有可觀察的訊號**：

| 方向 | 訊號 |
|---|---|
| **過度共用** | 參數增生，尤其是**只被一個呼叫端使用**的參數（`variant`、`isCompact`、`mode="legacy"`）。嚴格版：元件的分支邏輯取決於**誰**在呼叫它 → 它不是一個元件，是 N 個元件穿同一件外套。另一個訊號：不稽核所有呼叫端就不敢改它 —— 這個共用只生產了耦合，沒生產出重用價值 |
| **過度獨立** | **同一個修正要在 N 個地方各做一次**。注意訊號不是「存在重複程式碼」，而是「一個 bug 修了 N 次」—— 這正是 KNOWN-ISSUES `關聯` 欄位在偵測的東西（見 D6） |

**新開發的預設：先重複，第三次出現再抽。**

理由是不對稱性 —— **重複很便宜，錯誤的抽象很貴**。拆開已共用的東西比事後抽出共用的
東西難得多，因為發現抽錯時已經有 N 個呼叫端依賴那個形狀。而「等第三次」不是因為
重複好，是因為**第三次才是第一次看得見變異的軸在哪**；只有兩個樣本時無法區分
「因同一理由相同」與「碰巧相同」，而抽象的品質完全取決於有沒有抓對那個軸。

**附帶規則：共用的東西不該知道呼叫它的是誰。** 一旦它需要知道（`variant="checkout"`），
就把行為傳進去（slot／children／callback）而不是傳旗標。這樣即使共用判斷做錯，
被鎖住的只有「形狀」不是「行為」，拆起來便宜很多。

**為什麼不是「開頭就決定分層分類法」**：atom／molecule／organism 這類分層描述的是
**結果**不是**決策程序** —— 它告訴你東西該放哪裡，前提是你已經知道它的耦合程度，
而那正是開頭時唯一不知道的事。分層是耦合判斷的產物，不是輸入。

**日期**：2026-08-06

## D6 — 復發形態當架構訊號：用排序，不用門檻（已決議）

**問題**：KNOWN-ISSUES 的 `關聯` 鏈能指出「缺一個抽象」，但多長算警訊？

**決議 1：看的是「散佈度」，不是「長度」。**

長度把兩件診斷相反的事混在一起：

| 觀察 | 診斷 |
|---|---|
| 同一形態、**同一個地方**、復發三次 | 不是架構問題，是**修了沒守住** → 指向 `守備` 的品質 |
| 同一形態、**三個不同地方**、各一次 | 才是架構訊號 → 同一份知識散落多處，且已證明有人沒記得 |

所以要看的是**這條鏈碰到幾個不同的 `影響範圍`**。

**決議 2：不設門檻，改成排序。** 歸檔掃描產出不符合清單時，
把鏈按散佈度由高到低排，報前幾條。

**為什麼不是門檻**：`散佈度 > 3` 跟被推翻的「行數 > 400」有一模一樣的失效模式 ——
絕對數值撐不過不同的專案形狀，小專案永遠不觸發、大專案天天觸發，然後大家學會忽略它。
更關鍵的是它過不了「這個數字會改變什麼行動嗎」的檢驗：門檻觸發後的行動是「考慮重構」，
而重構做不做實際上由成本／時程／影響半徑決定，門檻數字根本不進入那個決定。
**不改變任何行動的數字是裝飾。** 排序沒有校正問題、不會因規模失準，
且回答的是真的會被執行的問題：「如果只能處理一條，處理哪條」。

**決議 3：訊號的讀法是「這份知識該換成機制」，不是「這裡該抽一個元件」。**

有些形態天生散佈很廣而且是對的（邊界錯誤處理、權限檢查、記錄、編碼轉換）。
若訊號一響就抽元件，這個機制會親手生產出 D5 說很貴的那個東西 —— **過度共用**。

| 機制 | 適合什麼 |
|---|---|
| 抽共用元件／函式 | 知識有明確單一位置可放，且呼叫端不需客製 |
| 型別／schema | 形態是「資料形狀被誤解」 |
| lint／靜態檢查 | 形態是「該做的事忘了做」（天生散佈廣的那類） |
| 測試模板／fixture | 形態是「每個新地方都要重驗同一件事」 |
| checklist（明確接受靠人） | 成本不值得自動化，但要寫下來 |

最後一列很重要：**明確選擇「這條靠人記得」是合法的結論**，只要它被寫下來。
那跟「沒想過」是兩件事。

**已知限制**：`關聯` 靠人手填，會被忘記（尤其隔幾個月的同形態，當事人根本不知道有前例
—— 那正是這個檔案要解決的問題本身）。所以**散佈度只會低估，不會高估**：
散佈度低**不可以**讀成「這裡健康」。補救是除了跟著 `關聯` 走，
另外用 `症狀`／`根因` 的**措辭** grep（「回 0 筆」、「吞掉」、「靜默失敗」）。

**日期**：2026-08-06

## D7 — KNOWN-ISSUES 結構檢查腳本的範圍（已決議）

**問題**：能不能寫腳本驗證條目記錄的關聯性是否屬實。

**決議：可以，但腳本只驗「結構」那一層，且不得以「驗證關聯性」為名。**

「關聯性是否如記錄」拆成三層，可驗性差距極大：

| 層 | 內容 | 可驗？ |
|---|---|---|
| **結構** | 指向的 `K-n` 存在；archive anchor 有效；**關聯群組原子性沒被破壞**（一條鏈只搬走一部分）；鏈上有 `已知未修` 卻被歸檔；`守備` 的測試存在且為綠；**`影響範圍` 提到的檔案是否還存在** | **完全可驗，且是腳本唯一真正的價值** |
| **語意** | 「K-8 和 K-3 真的是同一形態嗎」 | 不可驗。只能人／Claude 讀 —— 但這層不是靜默失效，讀了就知道 |
| **漏連結** | 該連而沒連的條目 | 不可判定。可做措辭相似度**提示**，必須標成「候選，請人看」而非錯誤，否則有人會為了消警告亂連 |

**為什麼價值集中在結構層**：那一層的失效全都是**靜默的** ——
原子性被破壞沒有任何外顯症狀，人眼掃過去看不出來；檔案改名後條目看起來完全正常。
人眼抓得到的東西寫成腳本收益很低。

**最大的實務風險：靜默綠燈。** 這類文件檢查腳本最常見的死法不是誤判，
是解析不到東西 → 0 則條目 → 0 個錯誤 → 綠燈，而且完全無聲。兩道防線：

1. **條目數斷言** —— 解析出的條目數必須等於 `^### K-` 的行數，不等直接報錯
2. **腳本自己要有轉紅紀錄**（鐵則 4）—— 準備故意壞掉的 fixture
   （指向不存在的 ID、只搬走半條鏈、守備指向不存在的測試），確認每一種都被抓到

**命名**：叫 `check-known-issues-links` 或「結構檢查」，**不要叫「驗證關聯性」** ——
綠燈會被讀成「關聯是對的」，那是它永遠做不到的宣稱。輸出裡要寫明**沒檢查什麼**。
一個檢查不能宣稱它沒檢查的東西（鐵則 9）。

**檔案存在性檢查的輸出語意**：它抓到的**不是「可歸檔」，是「這則需要人判斷：
形態還在嗎」**。腳本可以指出事實（檔案不在了），不能推論結論（所以過期了）。
報成歸檔候選會直接生產 D1「已定案部分的修正」講的那個最糟失效。

**附帶決定：`關聯` 維持單向（新指舊），由工具做遞移閉包**，不要求雙向對稱。
要求人回頭改舊條目（而舊條目可能已歸檔）違反「不刪既有紀錄」的精神，
且新指舊是自然的書寫方向，反過來要求會被忘掉 —— **會被忘掉的規則等於沒有規則**。

**何時寫**：格式已釘死在 `record` SKILL.md 的條目範本，所以解析不是憑空猜，
結構檢查現在就寫得出來。但**有門檻、有啟發式的部分仍要等真實樣本**
（`影響範圍` 的措辭習慣、鏈的實際形狀）。

## D8 — 回報的詳細度對應強度（已決議）

**問題**：每輪都寫完整四段回報，是否過度消耗 token 與 context。

**實測**（2026-08-06，以本 repo 一次兩檔的文件改動為樣本）：

| 項目 | 字元數 | 佔比 |
|---|---|---|
| 讀進 context 的檔案 | ~18,700 | 43% |
| 產生的 diff | ~22,800 | 52% |
| **回報本身** | ~2,500 | **~6%** |

**決議：保留四段格式，但詳細度對應強度** —— L0／L1 的 `改了什麼`／`為什麼`
由 commit 訊息承擔，L2 以上的主體寫進 `docs/tasks/` 計畫檔，對話只放結論。
`怎麼驗的`／`沒做什麼` 任何強度都不可省。

**為什麼不是「精簡或取消格式」**：

1. 回報只佔約 6%，砍到零省不了多少；真正吃 context 的是檔案內容與 diff，那是工作本身
2. 要跟**替代方案**比而不是跟零比 —— 沒有回報的話，讀 diff 比讀回報貴約 9 倍，
   而追問「你剛改了什麼」會觸發重讀檔案，**比一開始就寫回報更貴**
3. `沒做什麼` 的內容**只存在於回報裡**（diff 和 git log 都沒有）；
   `怎麼驗的` 是擋住「宣稱驗過但沒驗」的**機制**，拿掉它是移除一道檢查而非省字

**為什麼仍要改**：問題不在格式，在**沒有照既有的「詳細度可以縮」去縮** ——
對兩檔的文件改動用了 L2 規格的兩張表格。同時，回報寫在對話裡是**每輪付租金**，
寫進 commit／`docs/` 是**付一次、要看再撈**，且 compact 之後仍在。

**已知代價**：`CLAUDE.md` 因此從 140 行增至 146 行，離 D2 訂的 ~130 行更遠。
未處理，見 D2 的附帶決定。

## D9 — 變更清單加穩定 ID，只在 L2 以上用（已決議）

**問題**：多檔案變更事後要精準指涉「哪一項變更」很難，只能用模糊的檔名或描述回查，
跟本規範自己在 `KNOWN-ISSUES.md`（`K-n`）、本檔（`D-n`）已經證明有效的
「唯一 ID → grep 精準命中」模式不一致。由使用者在 mcp-fda 實測時提出。

**先排除一個容易混淆的選項**：不是把 `CLAUDE.md` 回報格式的四個類別
（`改了什麼`／`為什麼`／`怎麼驗的`／`沒做什麼`）換成編號。測過兩種編號效果完全不同——
類別編號只是換符號，標籤跟數字字元數相近，**不省 context**；`1`/`2`/`3`/`4` 到處都在用，
不是獨特錨點，對回查沒有幫助。真正有效的是**給被指涉的對象（每一項變更）配 ID**，
不是給結構本身編號，跟 D8 的「詳細度對應強度」是不同的軸，兩者不衝突、互補。

**決議**：`plan` skill 的 L2 任務計畫檔模板，「變更清單」表格加一欄 `ID`：

```markdown
## 變更清單
| ID | 檔案 | 變更性質 |
|---|---|---|
| C1 | ... | ... |
```

- ID 只需要在**這份任務檔內**唯一，不用像 `K-n`/`D-n` 那樣全專案唯一
  （任務檔本身已經用日期前綴＋檔名做了時間/範圍的分隔）
- 之後在對話或「完成紀錄」／「問題紀錄」表裡可以直接說「`C3`」而不用重新描述那項變更
- **只在 L2 以上用**。L1／L0 是單檔小改動，沒有多項可回查，加 ID 是過度工程

**為什麼不是「現有的變更清單表格已經夠」**：現有表格只有「檔案／變更性質」兩欄，
同一檔案在同一任務裡改兩次（邊做邊修很常見）時，表格列會重複或混在一起，
沒辦法單獨指涉「第二次改的那部分」。加 ID 解決的正是這個。

**代價**：多一欄要維護，ID 要遞增、不重用（跟 `K-n`/`D-n` 同一套規則，但範圍限縮在單一任務檔內）。

**日期**：2026-08-06
