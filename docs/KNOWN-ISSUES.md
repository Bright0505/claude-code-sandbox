### K-12 收尾寫「不需發版」時，沒有當場重跑量測，複述的是早幾個 commit 前的結論

- **影響範圍**：任何橫跨多個 commit 的任務，在收尾判斷「產品檔有沒有漂移」時；
  尤其是 `release` skill 的「發佈前判斷要不要發版」這一步
- **狀態**：已修（無守備 —— 文件性質的誤判，沒有可 mutation 驗證的斷言，
  **永不歸檔**，見 `record` §7）
- **症狀**：`docs/tasks/2026-09-17-docs-staleness-audit.md` 在 commit `e3d67f4`
  寫下「掃描確認 `dev` 與 `main`(v0.2.1) 的產品檔 diff 為空，不需要發版」——
  但那個 commit 自己的變更清單（C3-C6）就是在改 `README.md` 與
  `.env.claude.example`，兩者都在 `PROD` 清單裡。之後兩個 commit
  （`608464b`、`72fde24`）又各自加了新的 `PROD` 檔案改動，但收尾的結論
  沒有跟著重算，一路原樣抄到「沒做什麼」那一節。跑 `/release` 時實測
  `git diff --stat v0.2.1 dev -- README.md .claude/skills/release/SKILL.md`
  → 兩個檔案共 11 行改動，直接推翻先前的結論
- **根因**：無法從現有證據判定當時具體怎麼算的（不編造原因）。可歸納的形態是：
  「不需發版」這句話被當成**這批工作的既定結論**複述了三次（範圍說明、驗收勾選、
  沒做什麼），但它的量測對象（`main..dev` 的 diff）每多一個 commit 就會變 ——
  是一個需要在**最後一個 commit 之後**重跑才有效的斷言，不是可以在中途算一次
  就沿用到底的性質
- **判準**：
  ① 「不需要發版」這類收尾斷言，若任務橫跨多個 commit，要在**最後一個 commit
  落地之後**重跑一次量測指令，不能沿用中途某次的結果 —— 跟「沒紅過的測試不算
  測試」同一個道理：沒有對著最終狀態重跑過的斷言不算驗證
  ② 寫下這類結論前，先跟**同一份任務檔自己的變更清單**做一次交叉比對 ——
  變更清單若列了任何 `PROD` 內的檔案，「產品檔零改動」這句話在寫下的當下
  就已經自我矛盾，不需要外部證據就能抓到
  ③ 自檢訊號：一句話在同一份文件裡被複述三次而没有一次附上重新執行的指令輸出 ——
  複述不是驗證
- **關聯**：與 `K-9`（發佈清單覆蓋率）、`K-10`（讀反狀態欄位）同屬「稽核／引用的
  涵蓋範圍小於宣稱」，差別在本則是**斷言的時機**錯了（該對最終狀態重算時，
  用了中途的舊結果），不是清單漏項或讀反欄位
- **日期**：2026-09-17

### K-11 決議紀錄裡的「檔案:行號」指標，會被該決議自己的實作打掉，而且指向反面

- **影響範圍**：`docs/DECISIONS.md`（`D12` 的問題敘述）；以及任何用 `檔案:行號`
  描述「開立當下現況」的紀錄
- **狀態**：已修（無守備——文件性質的修法，沒有會轉紅的斷言，**永不歸檔**）
- **症狀**：`D12` 的問題段寫「sandbox 目前刻意沒有 docker CLI、不掛 socket
  （`README.md:59`、`sandbox.sh:29`）」。這則決議實作落地之後，`README.md:59`
  落在「設計重點」那一節，其中一條正是「不掛 docker socket，**但 docker 指令可用**」；
  `sandbox.sh:29` 變成 host 端的 `command -v docker` 檢查（跟容器內有沒有 docker 無關）。
  兩個指標都還**解析得到** —— 指到的是完整、通順、正常的句子，只是意思相反
- **根因**：一般的行號漂移是隨機的（指到不相關的行）。這裡不是：決議紀錄引用的
  「現況」**正是這則決議要改掉的東西**，所以實作一落地，那個位置必然被改寫成新的、
  相反的狀態。失準的方向由機制決定，不是運氣
- **判準**：
  ① 決議紀錄描述「開立當下的現況」時寫**形態與檔名**，不寫行號；要精準就寫
  commit hash —— 它不會動
  ② 行號只適合引用**不會被這則決議改動**的位置
  ③ 自檢訊號：**這個指標指向的東西，是不是正好是我要改掉的？** 是 → 不要用行號
  ④ 這類失效騙得過「指標還解析得到嗎」這種檢查 —— 檔案在、行號在、內容通順，
  只有語意反了。要抓到它只能讀指向的內容，不能只驗它能不能解析
- **關聯**：與 `K-8` 同屬**載體看起來完好、但對實際的讀者失效**的形態
  （`K-8` 是開機 log 傳不到容器內的 agent；本則是指標解析得到卻指向反面）
- **日期**：2026-09-17

### K-10 引用一份有狀態欄位的紀錄時，只取內容不取欄位，語意會整個反轉

- **影響範圍**：`CHANGELOG.md`、`docs/tasks/`；以及任何「條目的狀態由它所在的
  **欄位／小節標題**承載、而不是由內文承載」的紀錄格式
- **狀態**：已修（無守備——同 `K-11`，**永不歸檔**）
- **症狀**：`docs/tasks/2026-09-12-release-v021.md` 兩處寫「整套 suite 是 Linux-only
  （見 v0.1.0 的 CHANGELOG），這台 macOS host 跑不完」，並**據此把驗證降級成只跑
  `bash -n`**。但 `v0.1.0` 的 CHANGELOG 把那件事列在「**修正**」欄位下 —— 記的是
  這個缺陷**已經被修掉**（commit `9ee835c`：bash 3.2 把全形括號吃進變數名、
  `find -printf` 的 stub 補上，兩個根因逐條修完）。`README.md`「腳本的執行層」
  同樣把那兩支測試歸在 **host** 層。三個載體一致，任務檔是唯一的異常值，
  而它引用的正是那份說相反話的 CHANGELOG
- **根因**：引用時取了條目的**內容**，沒取它所在的**欄位**。在 CHANGELOG 這種格式裡，
  「這件事現在是什麼狀態」完全由欄位承載（「修正」vs「已知未驗」），
  而兩種狀態底下的**內文可以一字不差** —— 缺陷描述本身不帶狀態
- **判準**：
  ① 引用有狀態欄位的紀錄（CHANGELOG 的「修正」／「已知未驗」、KNOWN-ISSUES 的
  `狀態`）時，**把欄位名一起抄進引用處**。只抄內容的話，讀者（包括三版之後的自己）
  會自行補上一個狀態，而補錯的方向是固定的
  ② 自檢訊號：**引用一份紀錄來論證「某件事做不到」時，先確認那份紀錄不是在記
  「這件事已經被修好了」** —— 這兩者的原文可以完全相同
  ③ 這個錯誤是**單向**的：它只會把「已修」讀成「還在」，從而多跳過一次驗證；
  不會反過來讓人多做驗證。所以它的代價全部落在覆蓋率上，且完全無聲
- **關聯**：與 `K-9` 同屬**稽核／引用的實際涵蓋範圍小於它宣稱的範圍**的形態，
  但失效方式相反 —— `K-9` 是掃不到（零命中），本則是掃到了卻讀反
- **日期**：2026-09-17

### K-9 發佈的產品檔清單是白名單，漏掉新檔案時所有守衛都是綠的

- **影響範圍**：`release/release.sh`（`PROD` 陣列）；以及任何用**手維護的白名單**
  決定「哪些東西要被搬過去」的機制
- **狀態**：已修
- **守備**：`release/release.sh`::`守衛 0` —— 對 `dev` 的頂層條目做覆蓋率斷言，
  `PROD` ∪ `NOT_SHIPPED` 沒蓋滿就 `die`（實測轉紅：把 `Dockerfile.proxy` 從 `PROD`
  拿掉，腳本中止並列出該檔名；放回去就通過）
- **症狀**：`v0.2.0` 發佈前的稽核發現 `Dockerfile.proxy` 與
  `docker-compose.claude.docker.yml`（`v0.2.0` 這個版本的主要交付）不在 `PROD` 裡。
  照原樣發佈的話，`main` 上會有一份 `sandbox.sh`，它**預設**帶
  `-f docker-compose.claude.docker.yml` 而那個檔案不存在 —— 套用端一啟動就壞。
  而發佈當下**三道守衛全綠**：守衛 1 只驗「匹配數 > 0」（舊清單照樣匹配得到
  十幾個檔案），守衛 2／3 只看 `docs/`
- **根因**：白名單機制天生只驗「列出來的東西在不在」，驗不了「該列而沒列的東西」。
  `git checkout dev -- "${PROD[@]}"` 對於**根本沒被提到**的路徑不會有任何抱怨，
  所以「忘了加進清單」這個失誤在發佈端沒有任何觀察面
- **判準**：
  ① 白名單決定「搬什麼」時，光驗白名單裡的項目有效是不夠的 —— 要對**來源側的全集**
  做一次覆蓋率斷言：全集 = 白名單 ∪ 明列排除清單，有殘留就中止。
  沒有「明列排除」的話，排除就退化成「沒想到」，跟漏掉分不出來
  ② 「新增一個檔案時要記得更新清單」不能靠紀律 —— 它跟本檔 K-5 同一個形態
  （機制存在但要人主動觸發），差別在這裡連錯誤訊息都沒有
  ③ **同一個形態也發生在稽核指令本身**：`release` skill §3 的引用審計 grep 原本只掃
  `.md` 那幾份，掃不到 `sandbox.sh`／`scripts/entrypoint.sh` **註解**裡的 `K-5`
  （2026-09-03 由第二角度複讀抓到，不是 grep 抓到）。**稽核的範圍要等於出貨的範圍** ——
  兩份清單各寫一次就會漂移，而漂移的方向永遠是稽核比出貨窄
- **關聯**：與 K-5 同形態（要人主動記得的步驟＝會被忘記的步驟），
  差別在 K-5 漏掉時使用者看得到「連不到」的症狀，本則在發佈端完全無症狀
- **日期**：2026-09-03

### K-8 開機時才印一次的指引，容器內工作的 agent 看不到——只有啟動容器的人看得到

- **影響範圍**：`scripts/entrypoint.sh`（`print_docker_summary`、`print_network_summary`）、
  `README.md`「兩件要知道的事」；以及任何「靠 PID 1 開機時的 stdout 傳遞操作規則」的設計
- **狀態**：已修（無守備——文件性質的修法，沒有對應測試能守住，見下方判準第②點）
- **症狀**：`README.md` 與 `entrypoint.sh` 都已經正確講了「操作專案自己的 docker compose
  要先 `cd` 到 `$SANDBOX_HOST_WORKSPACE`，否則 bind mount 會被 proxy 拒絕」，且是
  K-5 修好後的產物（兩種狀態都印）。但套用端（`ggr` 專案的升級任務）實測時，**在容器內
  工作的 Claude session 一樣先撞到 `Binds: ... is outside ...` 才發現這件事**——因為
  session 是透過個別 tool call 跟一個**已經在跑**的容器互動，讀不到 PID 1 在容器啟動
  瞬間打印的那份 stdout。K-5 解決的是「使用者會不會誤讀成環境故障」，這裡是**同一個
  訊息換了一種讀者、對那種讀者等於沒印過**
- **根因**：K-5 的解法隱含假設「印出來」的讀者是**啟動這個容器的人**（看得到終端機輸出）。
  但實際操作 docker 指令的是**在容器裡工作的 agent**，這是另一個讀者，沒有管道讀到
  開機當下的 stdout——env var（`$SANDBOX_HOST_WORKSPACE`）本身隨時查得到，
  但「要主動去查」這件事本身需要**先被告知**，而開機 log 傳不到這個讀者手上
- **判準**：
  ① 任何要讓「在容器裡工作的 agent」（不是「啟動容器的人」）知道的操作規則，
  不能只印在 entrypoint 開機當下的 stdout——那個管道只有人類操作者讀得到。
  要嘛寫進**每輪都會被載入的地方**（`CLAUDE.md`），要嘛做成 agent 可以隨時主動查詢
  的東西（例如指令碼、固定路徑的檔案），不能只靠「啟動時印過一次」
  ② 這類文件性的修法沒有可 mutation 驗證的測試——`CLAUDE.md` 有沒有那一行，
  沒有一個會轉紅的斷言，所以標記「已修（無守備）」，**永不歸檔**
- **關聯**：與 K-5 同一種「印出來但讀者接收不到」的形態，差別在讀者身分不同
  （K-5 是「沒接上網路的人」看到「什麼都連不到」而不知道少了一個旗標；本則是
  「容器裡的 agent」讀不到「啟動當下才有」的輸出）
- **日期**：2026-09-02

### K-5 機制存在但預設路徑難用，於是「沒啟用」被誤判成「環境故障」

- **影響範圍**：`sandbox.sh`、`docker-compose.claude.network.yml`、
  `scripts/entrypoint.sh`；以及任何「留了選用機制但沒做成預設路徑」的設計
- **狀態**：已修
- **守備**：`scripts/entrypoint.sh`::`print_network_summary` —— 兩種狀態都會印出一行，
  「沒接上網路」不再是無聲的。`sandbox.sh` 則讓接上網路變成預設路徑
- **症狀**：一個 session 在 sandbox 內判定「no network/docker access to the live
  infra」，據此把交接文件上多項工作標為 `literally not executable from here`，
  並要求使用者改變工作方向。實際上專案服務全部正常運行中 —— 只是 sandbox 啟動時
  漏了 network overlay。實測三種症狀同時出現：服務名 `curl` exit 6（解析不到）、
  直接打 IP exit 28（逾時，封包被 `OUTPUT DROP`）、`localhost:<host port>` exit 7
- **根因**：兩層。表層是要正確啟動得同時記住兩個 `-f`、`WORKSPACE_DIR`、
  `APP_NETWORK_NAME` 四件事，且舊版 README 還要求專案改自己的 compose 把網路
  改名 —— 選用機制的門檻高到實務上等於預設關閉。深層是**這個失敗沒有任何輸出**：
  沒有錯誤、沒有警告，只有「什麼都連不到」。而「什麼都連不到」最自然的解釋
  就是環境壞了，不是「我少帶了一個參數」
- **判準**：
  ① 判定「環境沒有 X 能力」之前，先確認**自己處在哪個環境切面** ——
  容器內先看 `ip -4 -o addr show` 的網段、對照目標服務的網段，再下結論
  ② 設計面：**選用機制若沒有預設路徑，就要有失敗時的明確輸出**。
  兩者都缺時，使用者會用「整個壞了」來解釋，而那個解釋會擴散成錯誤的工作決策
  ③ 自檢訊號：**結論是「這件事做不到」而不是「這件事失敗了」** ——
  前者是能力判斷，需要比後者更強的證據
- **關聯**：無同形態條目。本則是**執行環境**的失效（不是規範文件自己的失效形態）
- **日期**：2026-08-12

### K-7 HTTP keep-alive 讓「一條連線一個請求」的假設靜默失效

- **影響範圍**：`scripts/docker-api-proxy.py`（HTTP 轉發層）；以及任何
  「解析第一個請求後就把 socket 原樣轉發」的 proxy／記錄器
- **狀態**：已修
- **守備**：`scripts/test-docker-api-proxy.py`::`force_close appends Connection: close`
  ／`force_close drops keep-alive headers`
  （mutation 驗證：把 `force_close` 拿掉、改回原樣轉發 → 三條斷言轉紅）
  以及 `Handler._exchange` 對非 upgrade 請求**不轉發 client→daemon 方向**
- **症狀**：同一個錯誤在同一個 session 內犯了兩次，兩次都無聲：
  ① 量測用的記錄器只記到每條連線的第一個請求，於是 `docker compose up -d`
  的端點清單只剩一個 `HEAD /_ping`。那份清單**格式正常、看起來完整**，
  漏了九成，差點被當成決策依據
  ② 過濾 proxy 的端點白名單完全正確，但只作用在第一個請求上。實測
  `docker pull`（`POST /images/create`，不在白名單）與 `docker inspect`
  一個屬於其他 compose project 的容器，**兩者都成功** —— 因為 docker CLI
  先送 `HEAD /_ping`，通過之後第二個請求走原樣轉發的 socket 穿透過去
- **根因**：docker CLI 對同一個 daemon 重用 TCP 連線。`scripts/docker-api-proxy.py`
  原本讀完第一個請求就把兩個方向交給 raw relay，而 relay 不認識 HTTP 邊界
- **判準**：
  ① **驗 proxy／過濾器一定要測「該被拒絕」的案例**，而且要測在
  **同一條連線的第二個請求**上。只測允許案例時，一個完全失效的護欄
  會呈現 100% 綠燈 —— 允許案例本來就該過
  ② 攔截層若要「批准後轉為原樣轉發」，先問**這條連線之後還能不能出現
  新的請求**。能就是漏洞。可行的收法有兩個：強制 `Connection: close`，
  或不轉發 client→server 那個方向（本檔兩個都做）
  ③ 量測工具本身要有**可否證的計數斷言**。「解析不到東西 → 0 筆 → 綠燈」
  是這類腳本最常見的死法（修正後同一批指令從 5 筆變 44 筆）
- **關聯**：與 K-5 同屬**失敗沒有任何輸出**的形態，但失效的層不同 ——
  K-5 是機制沒啟用，本則是機制啟用了卻只覆蓋一部分輸入
