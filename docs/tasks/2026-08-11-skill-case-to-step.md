## 目標

讓 skill 成為**可執行的步驟**，而不是案例的累積。

起因：skill 目前共 908 行，其中 `code`（100 行）與 `traps`（94 行）是純案例集。
案例舉例不完 —— 每個專案都能再補三則，一年後沒人讀得完。而這批文件的定位是
**公司內部開發流程的基準**，基準必須精簡到會被讀完。

## 範圍

包含：六個 skill 的內容收斂，分兩階段。
不包含：`CLAUDE.md` 本身、skill 的 `name`（觸發詞不動，避免破壞 skill 選擇）、
`docs/DECISIONS.md` 既有決議。

## 驗收

不用行數當判準 —— 行數是大小的代理，D6 已論證過大小 ≠ 傷害。改用：

1. **可執行**：每個小節都回答「我現在該做什麼動作」，不是「曾經發生過什麼」
2. **可移植**：拿掉專案專屬名詞（SDK 名、檔名、既有決議編號）後仍然成立
3. **無損**：逐條對照，現有案例教的判準一條都沒丟 —— 防止「收斂」變成「刪掉」

### 案例的去處（階段 2 定案）

原以為 `traps` 的案例要「搬家」到 KNOWN-ISSUES，實際處理後發現**不該搬**：
那五則都是「判準的佐證」，不是特定檔案的缺陷 —— 抽出判準後案例沒有獨立價值，
硬塞進 KNOWN-ISSUES 只會製造檢索雜訊（`record` §2 明文反對）。

**判準**：案例要進 KNOWN-ISSUES，必須有具體的 `影響範圍`（檔名／模組名）可供 grep。
沒有的，就是純粹的診斷心態，該留在 skill 裡當判準。

### 定稿的三條格式規則（階段 2 直接套用）

1. **實例一律不放。** skill 是規範不是案例集，保持中性才能跨專案套用。
   案例的去處是 `docs/KNOWN-ISSUES.md`（`record` skill 定義的「下一個人不知道會出事」），
   兩者職責不同：skill 說「該做什麼」，KNOWN-ISSUES 說「這裡踩過什麼」
2. **標題句型統一為「中文時機：術語」。** 中文時機讓人一眼看出「什麼時候用這條」，
   術語承載內容。純英文標題（如 `Syntactic similarity ≠ semantic equivalence`）
   雖然精準但犧牲可讀性
3. **`description` 盡量術語化**，但保留可被自然語言命中的觸發條件 ——
   它同時是給人讀的摘要與 skill 選擇的依據，全術語化會降低匹配率

### 術語判準（階段 2 直接套用）

**用術語的目的是不用解釋。** 一個詞若無法替掉一段解釋，它就沒有發揮作用；
用了術語卻還要補三條說明，代表**要嘛術語是多餘的、要嘛用錯了**。

因此每個術語下筆前確認兩件事：

1. **它的既定含義是什麼** —— `scope guard` 在 C++ 是資源清理，不是範圍控制
2. **它替掉了哪一段** —— 替不掉就別用，直接寫中文更誠實

階段 1 實際用上、確認正確的：`impact analysis`／`syntactic vs semantic`／
`spot check` vs `full verification`／`dead code elimination`／`mutation testing`／
`mutant`／`kill`／`scope creep`／`Definition of Done`。
