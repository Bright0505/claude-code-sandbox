## 目標

讓 skill 成為**可執行的步驟**，而不是案例的累積。

起因：skill 目前共 908 行，其中 `code`（100 行）與 `traps`（94 行）是純案例集。
案例舉例不完 —— 每個專案都能再補三則，一年後沒人讀得完。而這批文件的定位是
**公司內部開發流程的基準**，基準必須精簡到會被讀完。

## 範圍

包含：六個 skill 的內容收斂，分兩階段。
不包含：`CLAUDE.md` 本身、skill 的 `name`（觸發詞不動，避免破壞 skill 選擇）、
`docs/DECISIONS.md` 既有決議。

## 驗收

不用行數當判準 —— 行數是大小的代理，D6 已論證過大小 ≠ 傷害。改用：

1. **可執行**：每個小節都回答「我現在該做什麼動作」，不是「曾經發生過什麼」
2. **可移植**：拿掉專案專屬名詞（SDK 名、檔名、既有決議編號）後仍然成立
3. **無損**：逐條對照，現有案例教的判準一條都沒丟 —— 防止「收斂」變成「刪掉」

## 假設（若不對請說）

- 用工程通用術語（baseline／mutation／dead code elimination／scope guard／
  clean code）替代冗長中文描述。術語本身就是壓縮，且是這個領域的共同語言
- 每則保留**一行**去專案化的實例當錨點，不全刪 —— 沒有實例的判準讀起來像口號，
  但實例不該佔據篇幅主體
- 階段 1 只做 `code` 一個當試點。挑它不是因為最單純，是因為它**最能證明轉換
  成不成立**（5 節全案例、0 步驟）。形狀對了再推其他五個

### 階段 1 的觀察（供階段 2 參考）

- **收斂的槓桿是「時間軸」不是「刪字」**：舊版 5 節是 5 個平行案例，
  新版發現它們其實是同一條流程上的 5 個時點（估範圍 → 套用 → 改完 → 驗證 → 全程）。
  一旦排成時間軸，每節只需要一句話定位，解釋自然變短
- **工程術語是壓縮**：`dead code elimination`／`mutation`／`scope guard`／`clean code`
  各自替掉一整段中文描述，且是這個領域的共同語言
- **實例壓成一行引言仍有效**：保留「為什麼這條有用」，但不再佔篇幅主體
- 行數只掉 22%，但形狀完全變了 —— **再次確認行數不適合當驗收判準**（D6）
